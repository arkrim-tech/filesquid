# Implementation Plan: server (`filesquid-server` and the ciphertext-only hosted service)

This module plans two deployment types that MUST keep separate dependency graphs ([ADR 032](../../../../../resources/architecture/032-hosting-and-privacy-model.md)):

1. **`filesquid-server`** (`SV` rows): the owner-operated, multi-user Axum host. It mounts the `filesquid-api` router, serves the selected distribution's static UI from `FILESQUID_UI_DIR`, keeps accounts, groups and sessions in PostgreSQL, and stores files in a local or S3-compatible OCFL root. Until SV-F1.2 lands PostgreSQL, its activity journal is the interim SQLite store `<data dir>/filesquid.sqlite` from `filesquid-native`, which it links with default features only (journal store, data-directory checks, `HostMonitor`; never the `desktop` feature, enforced by `unit_native_features`) ([ADR 033](../../../../../resources/architecture/033-activity-journal-and-live-health-monitoring.md) amendment 2026-10-18). Its operator can read the files it stores; the UI MUST say so ([FileSquid U-20](../../../../../resources/product-vision.md#one-api-hosts-and-distributions)).
2. **The ciphertext-only hosted service at `*.filesquid.tech`** (`BE` rows, formerly the Axum mailbox): paid encrypted backup and sync. It stores and relays ciphertext only, authorises keys, fences OCFL head publication and records receipts. It MUST NOT depend on `filesquid_ocfl`, `filesquid_metadata`, `filesquid_c2pa`, the `filesquid-api` read paths over private plaintext, libvips or FFmpeg, MUST NOT parse OCFL and MUST NOT hold library keys ([BE-S-004](./srs.md), [TC-005](../../../../../resources/prd.md#tc-005-shared-rust-graph-hosted-mailbox-isolation-and-ocfl-writer), [T-054](../../../../../resources/product-vision.md#api-and-hosts)). Its binary and dependency-graph gate are created by SV-F4.1; Cargo features MUST NOT be the only boundary.

Cargo commands run from `apps/filesquid/` with `-p filesquid-server` (and `-p` for the hosted-service crate once SV-F4.1 creates it). Default bind `FILESQUID_BIND=127.0.0.1:8083`. Logs unbuffered JSON on stdout. Promtail MUST NOT be the collector ([ADR 014](../../../../../resources/architecture/014-stdout-observability.md)). Static UI files only; MUST NOT server-render private pages. Do not Dockerize Tauri from this module. Global sequence: [implementation-plan.md](../../../../../resources/implementation-plan.md).

- [ ] **Task SV-F1.2: Accounts, groups, sessions and collection permissions**
  - **Description:** PostgreSQL (SQLx migrations) for users, groups, sessions, personal and group-owned libraries and collection-level permissions, and the `activity_journal` table: implement `JournalStore` over PostgreSQL in this host and start the monitor with `filesquid_native::HostMonitor::start(postgres_store, Arc::new(DataDirChecks::new(data_dir)), ...)` instead of `HostMonitor::open`, so the server stops using the interim SQLite journal store while keeping `filesquid-native`'s default features (data-directory checks, `HostMonitor`) ([ADR 033](../../../../../resources/architecture/033-activity-journal-and-live-health-monitoring.md) amendment 2026-10-18). Operational data only; canonical file state stays in OCFL. `filesquid-api` checks permissions on every call (API-F1.7). Group membership MUST NOT grant ownership of personal libraries. RFC 3339 UTC timestamps. **Service-side fencing (acceptance criterion, owner decision 2026-10-18):** this is the first task that lets more than one writer share a library (more than one user with write access through group-owned libraries and collection permissions, together with API-F1.9), so it MUST close the writer-fencing gap that IO-0.6 left open ([OCFL-S-018](../../ocfl/resources/srs.md) "Known gap") before any library can be written by more than one user. A local filesystem cannot check a token, so the server refuses a stale fencing token in the same atomic step as each write, with this protocol: (1) implement `filesquid_ocfl::VersionReservations` over a PostgreSQL generation per object; (2) every storage mutation of a server library (each write under `vN/`, each delete made while reconciling an unpublished `vN`, each root write) runs inside one per-object write gate in the server process: inside the gate the writer reads the object's current generation from PostgreSQL, compares it with its own token, and only on a match performs that one mutation and leaves the gate, so no takeover can happen between the check and the mutation; (3) a takeover (a new holder raising the generation) also goes through that gate and waits at most a bounded time (default 30 s, configurable); if the old holder is still inside the gate when the bound is reached, the takeover is refused as `Held` and retried later, so the old holder's in-progress mutation finishes under a generation that is still current and is never a stale write; (4) a writer that stalled outside the gate and comes back after a takeover finds a newer generation inside the gate, so its late write, delete or root write is refused (`ReservationError::Lost`) and nothing reaches the storage; (5) only one server process writes a storage root, enforced by a PostgreSQL session advisory lock per root; a process whose lock session ends MUST close every write gate at once and MUST NOT write again until it holds the lock again, and a second process MUST NOT open the root for writing. A row lock or transaction held across the storage write is not this protocol, and a check made only by the writer before its write does not satisfy this criterion. For S3-compatible roots the storage-side criterion of IO-5.1 applies as well. Until the tests below pass, the server MUST NOT allow a second user write access to a library. Tests (PostgreSQL integration, local storage root): (a) writer A passes its own lease check and stalls before the gate, writer B takes over and publishes `vN`, then A's content write, delete and root write are all refused, no file is added or removed, and the validator reports no E023; (b) writer A stalls inside the gate, B's takeover is refused as `Held` after the bound, A's mutation completes, and B succeeds on retry after A releases; (c) a second server process cannot open the root for writing.
