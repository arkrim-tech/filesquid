# filesquid-ocfl

The OCFL module of FileSquid. It is a FOSS [OCFL 1.1](https://ocfl.io/1.1/spec/) library with a generic API; its commands are planned for the one FileSquid CLI, `fsquid` (Task IO-D.4), and it has no FileSquid or ImageSquid types. Digital preservation programmes can use the library on its own.

| | |
|---|---|
| Cargo package | `filesquid-ocfl` |
| Rust import | `filesquid_ocfl` |
| Path | `apps/filesquid/crates/ocfl/` (member of the `apps/filesquid/` Cargo workspace) |

FileSquid hosts reach this module through `filesquid-api`. The module itself MUST NOT depend on Axum, Tauri or another FileSquid module by default, and it MUST keep building for `wasm32-unknown-unknown` so the roadmap E2EE browser host stays reachable. Once Task IO-D.4 lands, independent programmes install the `fsquid` binaries from GitHub Releases. FileSquid MUST NOT shell out to `fsquid` for canonical OCFL I/O.

The crate stays independently publishable. It moves to its own repository only as part of extracting `apps/filesquid/` as a whole.

The Drive-style file browser that shows this module's storage facts (paths, versions, agents, digests, sizes) is part of `@filesquid/ui` in `apps/filesquid/ui/`.

## Storage backends

The engine reaches bytes only through the async, runtime-agnostic `storage::StorageBackend` trait ([OCFL-S-007](./resources/srs.md), [ADR 025](../../../../resources/architecture/025-client-side-filesquid-engines.md)). The host picks the backend; OCFL rules do not change.

| Backend | Targets | Feature |
|---|---|---|
| `storage::MemoryBackend` | every target, `wasm32` included | always on (for tests) |
| `storage::FsBackend` | native only | `fs` (default on) |
| S3-compatible | native and `wasm32` | planned (IO-5.1) |

- Operations: `put`, `put_if` (compare-and-swap with `Precondition::IfAbsent` or `Precondition::IfMatch(etag)`), `get_range`, `head`, `exists`, paged `list`, `delete`, and multipart `create_multipart`, `upload_part`, `complete_multipart`, `abort_multipart`. `delete` removes any key it is given; it is intended for staging and recovery, and the engine never uses it on published OCFL versions.
- The trait needs no executor. Its futures are `Send` on native targets and carry no `Send` bound on `wasm32`. `storage::complete_immediately` drives the futures of the in-memory and filesystem backends, which never wait, from synchronous code.
- Every transfer is bounded: ranged reads at most 8 MiB (`MAX_CHUNK_BYTES`), a single `put` at most 8 MiB (`MAX_PUT_BYTES`), multipart parts at most 64 MiB (`MAX_PART_BYTES`), at most 10 000 parts, so objects of at most 625 GiB (`MAX_OBJECT_BYTES`), and listing pages of at most 1 000 keys. Use `storage::ChunkReader` to read an object chunk by chunk and `storage::MultipartWriter` to write a large one part by part.
- Keys are `/`-separated relative paths; empty, absolute, `.`, `..`, backslash and NUL keys are rejected before any I/O.
- The shipped backends tag objects with the lowercase hex SHA-256 of their bytes.
- `storage::write_whole` writes a byte buffer of any size (single put, or multipart above 8 MiB, aborting a failed upload) and `storage::read_verified` reads one object back as a single version: the read is bracketed by two `head` calls and accepted only when both return the same entity tag (opaque tags such as S3 `ETag`s work), and backends that report `content_addressed_tags()` (the shipped ones) must also return bytes that hash to the tag; otherwise it retries up to 3 times. They suit small objects such as sidecars; stream large content instead.
- `storage::default_staging_dir(root)` picks `filesquid-ocfl-staging` in the system temporary directory, or the sibling `<root>.fsquid-staging` when the temporary directory lies inside the root (for example a root of `/tmp`); `FsBackend::with_default_staging(root)` uses it.

`FsBackend::new(root, staging)`:

- Resolves both directories (symbolic links, `.` and `..`) and refuses a staging directory that resolves to the root or inside it.
- Writes through a flushed temporary file that is renamed into place. Temporary files use the reserved `.fsquid-` name prefix; keys may not use it and listings skip it. Listings return regular files only, never links, FIFOs or other special files.
- Serialises every mutation of published objects (`put`, `put_if`, `delete`, `complete_multipart`) with an operating-system lock on a file in the staging directory, named after the resolved root. All writers to one root, in any process, MUST share one staging directory. Multipart staging (`create_multipart`, `upload_part`, `abort_multipart`) does not take this lock: each upload has its own directory under `staging/uploads/<sha256 of the resolved root>/`, so an upload ID from one root is unknown to every other root sharing the staging directory, parts are only written into an existing upload directory, and completing or aborting first renames that directory (an atomic step), so a late part can never reopen a closed upload. An abort never renames the directory back: a part write that was already inside it when it closed can add a temporary file during the removal, so the removal is retried up to five times, and a closed directory that still cannot be removed is left behind, closed, and reported as an error. Every internal path (staging, upload and lock directories, key records, parts, lock files, temporary files) and every object file is opened or created without following links, as a regular file only, with the open handle checked against the path (new files are created with `create_new`, which never follows or reuses an existing entry). Internal records are size-capped, and `create_multipart` refuses a key longer than that cap (64 KiB). `Precondition::IfAbsent` publishes with a hard link, which the operating system refuses when the target exists, so two creators never both win even without the shared lock.
- Refuses a key whose path below the root passes through an existing symbolic link. On Windows it also refuses drive and stream names (`:`), reserved characters, device names such as `CON` or `COM1`, and names ending in a dot or space. The checks run before each operation, so the root MUST NOT be writable by untrusted processes.

Path-based helpers (feature `fs`) keep their signatures for existing callers:

- `write_logical_file` and `read_logical_file` go through `FsBackend`. Reads use `read_verified`, so a file replaced mid-read is read again and never returned as a mix of two versions.
- `reject_git_in_ocfl_root` checks for a `.git` entry (directory, file or link, without following links) directly on the filesystem; it does not use a storage backend.

## Git guard

Git MUST NOT be the OCFL store, and the storage hierarchy MUST stay plain files ([OCFL-S-001](./resources/srs.md), [ADR 016](../../../../resources/architecture/016-rust-ocfl-library.md)). The guards can be run against every backend and target, `wasm32` included. They check only when called: backend reads and writes do not run them. `read::StorageRoot::open` and `read::Object::open` run them on every open (IO-0.4); other callers MUST run them when they open a storage root or an object, and before they publish a version (IO-0.6 onward).

**Scope (owner decision, 2026-10-18):** the guard covers the storage root, the storage-hierarchy directories between it and the object roots, and each object root. A `.git` inside an object's preserved content, such as an archived Git repository under `v1/content/`, is content the owner chose to keep, and the guard allows it. It may hold only ordinary files and non-empty directories: soft links, hard links and empty directories inside it are refused like anywhere else in the storage hierarchy.


- `check_storage_root(&backend)` runs the backend's hierarchy check, then pages through every key (at most `MAX_WALK_ENTRIES`, one million; a larger root is reported as over the limit, never passed). Each continuation must be the last key of its page and move forward; a backend that skips keys, sends an empty page with a continuation or stalls is refused, so no `.git` can be skipped. It refuses a `.git` entry in the storage root, in a storage-hierarchy directory above the objects, or in an object root (a directory holding an `0=ocfl_object_*` declaration that is not inside another object), and allows one inside object content (ordinary files and non-empty directories only, as above).
- `reject_git_in_root(&backend, root)` checks one storage or object root for a `.git` file or any key under `.git/`.
- `StorageBackend::check_hierarchy(prefix)` refuses soft links (`StorageError::SymlinkForbidden`), hard links (`HardLinkForbidden`), empty directories below the root (`EmptyDirectoryForbidden`) and other non-regular entries. Object stores have neither links nor directories, so the default implementation only validates the prefix. `FsBackend` walks the directory under its root write lock, with the same bounds as listings. Hard links are detected where the standard library reports link counts (Unix, macOS included); on Windows they cannot be seen yet and pass.
- An empty `.git` directory holds no keys; on a file system it is refused as an empty directory.

## OCFL file formats

Pure parsing and writing, available on every target, `wasm32` included ([OCFL-S-002](./resources/srs.md), [ADR 009](../../../../resources/architecture/009-cryptography-webcrypto-compatible-suite.md)):

- `digest::DigestAlgorithm`: `sha256` is the engine's algorithm (`DigestAlgorithm::ENGINE`), so objects it writes use SHA-256 and validators report OCFL's SHOULD-use-`sha512` warning (W004) for them. `sha512` is read, because OCFL 1.1 allows both and most existing objects use it. `hasher()` digests content in bounded chunks. `matches` compares two digests of the algorithm's length and hexadecimal digits without regard to case, as a sidecar check needs; inside an inventory a state digest must match its manifest key exactly (E050).
- `inventory::Inventory::parse(bytes)` reads one untrusted `inventory.json`. It refuses input above 64 MiB (`MAX_INVENTORY_BYTES`) before parsing ([OCFL-S-017](./resources/srs.md); these engine bounds carry no OCFL code), JSON nested deeper than 8 levels (`MAX_JSON_DEPTH`) while parsing, and any JSON object that repeats a key. It then checks every rule one inventory can decide and names the OCFL 1.1 validation code of the first one broken (`FormatError::code`): required keys (E036, E041, E043, E048), no other keys (E102), `type` (E038), `digestAlgorithm` (E025), `contentDirectory` (E017, E018, E108), version names, padding and sequence (E008 to E012, E104, E105), `head` (E040), `created` as RFC 3339, with a leap second only at 23:59 UTC (E049), `message` and `user` (E054, E094), manifest digests and content paths (E030, E031, E039, E092, E096, E099 to E101, E106, E107), state digests and logical paths (E050, E052, E053, E095) and fixity (E057, E097, E111). Digests keep the case they were written in, and a state digest must match its manifest key exactly. `to_json()` writes an inventory with sorted keys that parses back to the same value.
- `inventory::VersionNum`: `v1`, `v2`, ... or zero-padded `v001`, ...; OCFL sets no digit limit, so the number is a validated decimal string and any valid name parses. `next()` returns `None` rather than overflow a padded width; otherwise it returns a name `parse` accepts.
- Sidecars: `sidecar_name`, `sidecar_contents` (`DIGEST inventory.json` and a newline), `verify_sidecar` (refuses input above 4 KiB, `MAX_SIDECAR_BYTES`; E061 malformed, E060 wrong digest) and `check_sidecar_name` (E059).
- `namaste::Declaration`: `0=ocfl_object_1.1` and `0=ocfl_1.1`, with their exact contents (E007, E080).

Object-level validation (files against the manifest, version directories, earlier version inventories) is the `validate` module, built on these types ([Structural validation](#structural-validation)). `tests/integration/fixture_inventories.rs` checks the root inventories, sidecars and declarations of the [pinned OCFL 1.1 community fixtures](#pinned-ocfl-community-fixtures).

## Read and browse

The `read` module opens storage roots and objects through any storage backend, on every target, `wasm32` included ([OCFL-S-004](./resources/srs.md), [ADR 016](../../../../resources/architecture/016-rust-ocfl-library.md), [ADR 023](../../../../resources/architecture/023-filesquid-ocfl-engine-and-parquet.md)):

- `StorageRoot::open(&backend)` runs the storage-root guard, then checks the `0=ocfl_1.1` declaration (E069, E080; another version, such as `0=ocfl_2.0`, is `ReadError::UnsupportedVersion`; a root with more than 16 `0=` files is E069, and the scan keeps no more than 16 of their names) and, from the guard's one paged listing (at most `MAX_WALK_ENTRIES` keys), discovers the outermost object roots: directories with an `0=ocfl_object_*` declaration that are not inside another object. `objects()` lists them; `open_object(root)` opens one.
- `Object::open(&backend, root)` runs the Git guard and hierarchy check on the object root, requires exactly one object declaration among the files directly in the root, with exact contents (E003, E007), and refuses a root declared as another OCFL version (`ReadError::UnsupportedVersion`; OCFL 1.0 objects are out of scope, OCFL-S-011), reads the root inventory (E063 when missing; refused above 64 MiB before it is read) and its sidecar (E058, E060, E061; refused above 4 KiB before it is read), and requires the head version's inventory, when present, to be the same file (E064). A sidecar mismatch is read again, at most 3 times (`READ_ATTEMPTS`), in case a writer replaced the inventory between the two reads. Declarations above 64 bytes (`MAX_DECLARATION_BYTES`) are refused before they are read. Each of these small files is read as one consistent version and its size bound is checked on every attempt before any byte is read, so a file that grows during the read is never buffered past its bound. A head version inventory that disappears during the read counts as missing.
- Only the root inventory commits versions (ADR 016 "Published head (readers)"): content or a version inventory for a `vN` above the root `head` is unpublished, and pinning it is `ReadError::VersionNotFound`. A root inventory whose sidecar still holds the digest of the previous version's inventory (a writer is publishing, or crashed before writing the root sidecar) is not committed either: the object opens at that previous version and `Object::unpublished_head()` names the claimed head. Any other sidecar mismatch is E060.
- `Object::state(&version)` (or the pure `read::resolve_state(&inventory, &version)`) resolves the logical state of a version the caller pins through `state` and `manifest` only. A file whose bytes were stored in an earlier version resolves to that earlier content path; files the inventory does not list are never part of the state. Each `LogicalFile` has its logical path, digest and content path; the state has the object id and version.
- `Object::stream_file(&version, path, chunk_bytes)` returns a `LogicalFileReader` that reads in chunks of at most 8 MiB and checks the digest when the stream ends: bytes are unverified until `next_chunk()` returns `None`, and a mismatch or missing content file is E092. `Object::copy_file(&version, path, &dest, &key, precondition)` streams into a multipart upload on any backend and publishes it only when the digest matched; otherwise the upload is aborted, no new object is published at `key`, and any object already there stays unchanged. A copy never edits an OCFL object ([OCFL-S-019](./resources/srs.md)): before it writes, it refuses (`ReadError::CopyIntoOcflRoot`) a `key` that lies inside an OCFL object root or storage root on `dest`, that is, below any directory (or the backend root) holding an `0=ocfl_object_<version>` or `0=ocfl_<version>` declaration of any version, including versions the engine does not read. Each directory above `key` is asked with one listing of at most 1,000 keys under its `0=ocfl_` prefix. The filesystem backend reads that directory's entries and enters only subdirectories whose names start with `0=ocfl_` (whose keys can match the prefix); every other subdirectory is pruned unread, so the check never walks a whole storage root. Two bounds refuse a copy with `StorageError::LimitExceeded` before anything is written: a `key` deeper than 64 directory levels (`MAX_DESTINATION_DEPTH`), and a directory with more than 1,000 keys under that prefix and no declaration among them, which is refused rather than guessed. Copy out to a staging or export location instead; only the [writer](#write) changes an object, by adding a version. A refused copy logs one `tracing` warning (`refused a copy into an OCFL root`) with the `destination` and the declaring `root`, and names the object the copy concerns ([OCFL-S-025](./resources/srs.md)): `object` is the source object's identifier and `version` the version read, for `copy_file` and `ChangeModel::checkout`; a staging write names the object its change model was built for, with no `version`. A host can journal them as the object reference `<object>@<version>` when the identifier and version form a valid reference under its rules ([API-S-031](../api/resources/srs.md)); the engine does not check that. The refusal and its error are unchanged.
- `Object::history()` lists every version with `created`, `message` and `user`; `Object::diff(&from, &to)` lists added, deleted, modified and renamed paths (a rename is a deleted and an added path with the same digest), in path order.
- Reading is not validation: a reader refuses only the faults it meets. Structural validation is the `validate` module.

## Enumerate committed logical state

`StorageRoot::enumerate(versions)` enumerates the committed logical state of every object discovered when the storage root was opened ([OCFL-S-004](./resources/srs.md), [T-039](../../../../resources/product-vision.md#canonical-ocfl-state-and-evidence), [ADR 023](../../../../resources/architecture/023-filesquid-ocfl-engine-and-parquet.md) engine core item 6). A caller rebuilds its own catalog, or projects a dataset, from the storage root alone; the enumerator needs no SQLite, PostgreSQL or application type.

- It is a pull cursor (`CommittedState`): each `next_event().await` does one step and returns `Some(Ok(CommittedEvent))`, `Some(Err(EnumerateError))` or `None` at the end. It holds at most one object's inventory and one version's state, and reads no content bytes.
- `Versions::Head` (the default) enumerates each object's committed `head`; `Versions::All` every committed version the inventory lists, from the first through `head` (zero-padded names such as `v001` kept as written).
- Events come in a fixed order: objects in object-root order; per object a `CommittedObject` (root, id, head, digest algorithm, unpublished head), then each version oldest first as a `CommittedVersion` (object id, version, file count) followed by its `CommittedFile`s in logical-path order. A file event carries the object id, version, logical path, digest algorithm, digest and content locator: `content_key`, the storage key from the storage root of the bytes the manifest lists for the digest (unchanged bytes keep the key in the version directory where they were first stored).
- State comes from the committed root inventory, exactly as `Object::open` and `Object::state` read it: files the inventory does not list are never enumerated, and neither is a version above the committed head (an uncommitted root inventory shows as `unpublished_head`).
- An object that cannot be opened or resolved (a guard refusal, E003, E007, E058, E060, E061, E063, E064, an engine bound or a backend error) gives one `EnumerateError` with its root and `code()`, and the enumeration goes on with the next object, so one broken object does not hide the rest. Content digests are not checked here: stream a file (`Object::stream_file`) or validate the object for that.

`tests/integration/enumerate_state.rs` enumerates built objects on the in-memory and filesystem backends, and every pinned `good-objects` and `warn-objects` fixture stored in one storage root, comparing each with an independent reading of its inventory JSON and reading every locator back against its digest; bad fixtures among them are reported with their codes while the good ones still enumerate.

`tests/integration/fixture_reads.rs` resolves every version of every `good-objects` and `warn-objects` fixture and streams every logical file against its digest, and checks that a reader refuses the bad fixtures whose faults it meets, with the code their names list ([OCFL-S-010](./resources/srs.md) (a)), on the [pinned fixtures](#pinned-ocfl-community-fixtures).

## Structural validation

`validate::validate_object(&backend, root)` validates one OCFL 1.1 object through any storage backend, on every target ([OCFL-S-009](./resources/srs.md)). It returns a `ValidationReport`: each broken rule it reaches is a `Finding` with its OCFL 1.1 validation code (`E###` errors, `W###` warnings), the storage key (and JSON pointer, for an inventory value) where it is, and a message. `is_valid()` is true when there are no errors; warnings never make an object invalid. The function returns an error only when the object cannot be validated: a backend failure, a listing above `MAX_WALK_ENTRIES` keys, a file above the engine's parsing bounds ([OCFL-S-017](./resources/srs.md); no OCFL code), or an object declared as another OCFL version than 1.1.

It checks, in order:

- the hierarchy under the object root: an empty directory is E024 (validation goes on), a soft or hard link E090 (validation stops there, since the listing cannot be trusted);
- the declaration (E003, E007), the root inventory (E063 when missing, every code `Inventory::parse` gives, E038 for a type other than 1.1) and its sidecar (E058, E060, E061);
- the object root's entries: only the declaration, the inventory and its sidecar, version directories, `logs` and `extensions` (E001); a version directory the root inventory does not list is E046, even with an inventory and sidecar of its own, because only the root inventory commits a version; a listed version without a directory is E010; `extensions` holds only directories (E067), each SHOULD be a registered extension name (W013);
- inventory warnings: zero-padded versions (W001), `sha256` (W004), an id that is not a URI (W005), a version without `message` or `user` (W007), a user without an address (W008) or with one that is not a URI (W009);
- each version directory: only its inventory, its sidecar and the content directory (E015; another directory is W002 and ignored). When the version inventory parses, only the sidecar for its `digestAlgorithm` is allowed; a sidecar without an inventory is E015; a malformed inventory reports its own error and allows any recognised (`sha256`, `sha512`) sidecar; a missing inventory is W010; a version inventory must be valid with its own sidecar, name its own version as `head` (E040), keep the id (E037) and content directory (E019), not go back to an older specification (E103), equal the root inventory for the head version (E064), describe every earlier version's state as the root inventory does (E066; `created`, `message` or `user` differences are W011), keep every manifest path inside a content directory (E042) and list every content file of its versions (E023);
- content: every file in a content directory is in the manifest (E023), every manifest path is inside a version's content directory (E042), and every file is streamed once, in chunks of at most 8 MiB, and checked against every digest stated for it: the root manifest and the manifests of earlier version inventories, whatever their algorithm (E092), and the root fixity block (E093). A content path that does not exist is E092 (and E093 when the fixity block lists it).

Fixity values are checked in every algorithm of the OCFL 1.1 fixity table (`fixity::FixityAlgorithm`: `md5`, `sha1`, `sha256`, `sha512`, `blake2b-512`, E027); values in other algorithms are ignored (E028). md5 and sha1 are only read: the engine writes `sha256`.

One inventory is checked to its first broken rule, so an object whose inventory breaks several rules reports the first; the [fixtures README](./tests/fixtures/ocfl/README.md) allows this. Storage-root validation (E069 to E090 across a whole storage root) is not part of this module yet; `StorageRoot::open` checks the declaration and guards.

## Write

The `write` module publishes new versions through any storage backend, on every target ([OCFL-S-018](./resources/srs.md), [ADR 016](../../../../resources/architecture/016-rust-ocfl-library.md) "Write (forward delta)", [ADR 007](../../../../resources/architecture/007-durable-jobs-and-interactive-performance.md), [ADR 012](../../../../resources/architecture/012-s3-compatible-ciphertext-storage.md)). It is the engine's only write path; callers reach it through the [change model](#change-model), which drives `ObjectWriter::commit`.

- A `VersionDraft` names the next version's whole logical state: each path is staged bytes on the caller's staging backend (outside the storage root) or a digest the manifest already holds. Paths left out are deleted from the new state; their bytes stay.
- `ObjectWriter::new(&storage, &reservations, holder).commit(root, expected_head, &staging, &draft)` first assembles the version without writing: it hashes the staged bytes (sha256), builds the new inventory and refuses an invalid draft (`created` not RFC 3339 UTC, an unknown digest, another object's id, a path OCFL forbids) or a base that is not sha256. It then reserves `vN`, re-reads the committed head (`CommitError::HeadMoved` when it is not `expected_head`), runs the Git and hierarchy guards, and writes in this order: the declaration (new objects), each new bitstream under `vN/<contentDirectory>/` (`content` unless the base inventory names another; only digests the manifest lacks, once each), the version inventory and its sidecar, then the root inventory (compare-and-swap on the base) and the root sidecar last (compare-and-swap on the sidecar read before the root inventory was replaced). A base whose committed head has no version inventory of its own, or whose head version inventory has no sidecar, is refused (`CommitError::MissingVersionInventory`), and so is one whose head version inventory is not byte-identical to the committed inventory or whose head sidecar does not match it (`CommitError::VersionInventoryMismatch`), because readers need that file to read past an interrupted publication; see [Version-inventory repair](#version-inventory-repair-w010). Content is streamed in chunks of at most 8 MiB into parts of at most 64 MiB and re-checked against the assembled digest (`CommitError::StagingChanged`). Nothing under `vN/` is overwritten (`IfAbsent`).
- Every write is preceded by a fence check (`VersionReservations::confirm`). A writer whose reservation expired, was released or passed to another writer gets `ReservationError::Lost` at its next write: it writes no more content and never publishes the head.
- `LeaseStore::new(backend, prefix, clock, LeaseConfig { ttl_ms, margin_ms })` keeps one lease record per object in any backend with compare-and-swap, outside the storage root and shared by every writer of that root (for a local root, an `FsBackend` over a directory such as the staging directory). Each new holder gets a larger fencing token; a confirm renews the lease once less than half its TTL is left and fails once no more than the margin is left (defaults 60 s and 10 s). A host can implement `VersionReservations` over a PostgreSQL generation instead. `wasm32` callers pass their own `Clock`; native callers can use `SystemClock`.
- A crash while publishing `vN` of an existing object leaves `vN` unpublished: readers keep seeing `v(N-1)`. Until it is recovered, the validator reports what the crash left: the unlisted `vN` directory (E046) when the root inventory was not yet replaced, or the root sidecar that does not match the root inventory (E060) when it was. A crash during the first commit leaves no committed version: opening the object is E058 (or E063 before the root inventory is written), and only a commit for the same object id can recover it. After the crashed writer's lease lapses, the next commit of that version restores a root inventory that was never committed, keeps leftover content whose bytes match, deletes the rest of `vN/`, and publishes `vN` once.
- `CommitReceipt` (object id, version, `created`, inventory digest, content paths written, and `took_over`) is what the caller records in its own operational store; the engine owns no database. `took_over` is true when the commit's reservation replaced one that was still held, not released, when it expired or was reassigned (`Reservation::took_over`, which `LeaseStore` sets and every other `VersionReservations` store MUST set too, through `Reservation::with_takeover`; [OCFL-S-023](./resources/srs.md)): the previous writer crashed or stalled and may have left a stray file under a version directory, so the host validates the object at once (API-S-022). `RepairReceipt::took_over` reports the same for the version-inventory repair.

Fencing is checked by the writer, not enforced by the storage: a writer that stalls for longer than the margin between a fence check and its next write could still make that one write. It cannot replace another writer's content, inventories or head (writes under `vN/` never overwrite, and the root inventory and root sidecar are compare-and-swaps), but a file it adds under `vN/` after the new holder's last listing check would be published as an extra file that the validator reports (E023), and a stalled recovering writer could delete a file the new holder already verified. Choose a margin well above the longest single write. The owner accepted this gap on 2026-10-18 only while a library cannot be written by more than one host process or by more than one user ([OCFL-S-018](./resources/srs.md) "Known gap"; background in the [IO-0.6 Walkthrough](./resources/tasks/Task-IO-0.6-Walkthrough.md#remaining-limits)). Before that changes, a check that refuses a stale fencing token in the same atomic step as the write closes it; a check made only by the writer before its write does not. The S3-compatible backend carries a storage-side check (IO-5.1) and the multi-user server a service-side PostgreSQL generation check (SV-F1.2), each as an acceptance criterion. Until then, every validator error, E023 included, reaches the host's health status and the Monitor ([API-S-022](../api/resources/srs.md)).

### Version-inventory repair (W010)

A base whose committed head has no version inventory (W010) stays refused (`CommitError::MissingVersionInventory`). `ObjectWriter::repair_version_inventory(root)` is the one-time repair ([OCFL-S-020](./resources/srs.md)); the engine never runs it by itself, and opening, reading, validating, inspecting or copying an object never repairs it. The host runs it only after the owner consents and records it in the activity journal ([API-S-023](../api/resources/srs.md)).

- It reserves the object as a commit does, re-reads the root inventory under the reservation (`RepairError::RootChanged` when it moved) and runs every refusal check before its first write, also when resuming: the root sidecar must match the root inventory (`RootSidecarMismatch`), the Git and hierarchy guards must pass, the head version directory must hold nothing its inventory does not list besides the two repair files (`NotRepairable`), and the full validator must report no error except the head's missing version sidecar (E058) in the exact interrupted-repair shape below (`Invalid` for every other finding, content digest errors included).
- It then writes `v<head>/inventory.json` and last `v<head>/inventory.json.<algorithm>`, each byte-identical to the root inventory and root sidecar, with `IfAbsent` and a fence check before each write. No content, logical state, other version directory or root file changes, and no version is published.
- A crash between the two writes leaves the logical state unchanged. That exact shape (a head version inventory byte-identical to the root inventory, no version sidecar, no other unlisted file) is an interrupted repair: its only validator finding, the missing version sidecar (E058), is allowed, and running the repair again writes the sidecar only. Until then `commit` refuses the head too, because the version sidecar is missing. A head that already holds both files is refused with `NothingToRepair`; any other head version inventory or sidecar is `NotRepairable`.
- `RepairReceipt` (object id, version, digest algorithm, inventory digest, paths written, and `took_over`, as for a commit) is for the caller's journal. A repaired sha256 object becomes editable. A sha512 object, such as the pinned `W010_no_version_inventory` fixture, is repaired the same way but its commits are still refused (`UnsupportedAlgorithm`), because the writer extends sha256 objects only.

Run its tests (MemoryBackend and FsBackend, crash injection between the two writes) and its BDD feature:

```bash
cd apps/filesquid
cargo test -p filesquid-ocfl --locked --test integration_version_inventory_repair
cargo test -p filesquid-ocfl --locked --test features -- --name repair
```

## Change model

The `change` module is the git-like API every caller uses to make versions: the view API (IO-1.2) and `fsquid` (IO-D.4) call it, and there is no second write path ([OCFL-S-014 to OCFL-S-016](./resources/srs.md), [ADR 016](../../../../resources/architecture/016-rust-ocfl-library.md) "Change model (public API)"). It builds on `ObjectWriter::commit`, so every version still goes through the fenced `vN` reservation, the write order and the head compare-and-swap above.

- `compute_delta(inventory, base, working)` classifies a working state (logical path to sha256) against a base version by digest: `PathChange::{Added, Changed, Renamed, Deleted, Reinstated}`. A deleted path and a new path with the same digest are a rename; a new path whose content an earlier version held, but the base does not, is reinstated. Only added or changed content whose digest the `manifest` lacks is written (`new_bytes`); renames, deletes and reinstatements change `state` only.
- `StagingArea::new(&backend, prefix)` is where changes accumulate: `<prefix>/index.json` (format `filesquid-ocfl-staging` version 1: object id, base head, and per staged path either `{"sha256": ...}` or `{"removed": true}`) and `<prefix>/blobs/<sha256>` for bytes the object does not hold yet. Use one prefix per object and writer, on any backend outside the storage root (a directory on native, browser staging storage on `wasm32`). Before each first write the area refuses a key below an OCFL object or storage root; it is never an OCFL extension, and reading or recovering an object never needs it.
- `ChangeModel::new(&storage, &reservations, holder, root, object_id, staging)` offers `stage_bytes`, `stage_remove`, `stage_rename`, `stage_tree` (every file under a prefix of any backend becomes the working state), `reset`, `status` (the staged change set against its recorded base, and the current head), `diff(from, to)` between two versions, `log` (newest first), `checkout(version, &dest, prefix)` (refused inside an OCFL root), `commit(meta)`, `revert(version, meta)` (a new version with an earlier version's state) and `reinstate(version, paths, meta)` (a new version restoring chosen paths). A successful `commit`, `revert` or `reinstate` publishes exactly one version; the other operations publish none. Revert and reinstate point paths at existing manifest entries and never touch earlier versions. A change set that leaves the state as it is is refused (`ChangeError::NothingToCommit`). After publishing, `commit` clears the staging area only when its index is still the one committed; otherwise, or when clearing fails, it returns `ChangeError::StagingNotCleared` carrying the receipt, and `reset` clears it (refused, like every staging write, for a prefix inside an OCFL root).
- `stage_file(path, &source, key)` stages one logical file from the file at `key` of any backend (a directory on `FsBackend`, memory, or a remote store) and answers its sha256 digest ([OCFL-S-026](./resources/srs.md), IO-1.7). It streams: the file is read in chunks of at most `MAX_CHUNK_BYTES` (8 MiB) once to hash it and, only when its bytes are new, once more to copy it into the staging area while hashing again, in multipart parts of at most `MAX_PART_BYTES` (64 MiB). The stage's own buffering is bounded (one chunk and one part in memory at a time); only the upload's per-part completion records, one small entry per part up to `MAX_PARTS` (10,000), grow with the file. The staged blob lives in the staging backend: on disk or remote for `FsBackend` and remote stores, but a staging area on `MemoryBackend` (in-memory storage, which keeps every uploaded part until the upload completes) holds the whole staged file in memory by design, so a host stages large files on `FsBackend` or a remote store. Bytes the object's `manifest` holds are not copied; a blob the staging area already holds under the digest is re-hashed and reused when it matches, and replaced with the file's bytes when it does not (corrupt or stale), so no staged index entry points at bytes that do not match its digest. A file whose two reads differ is refused (`ChangeError::SourceChanged`) and its partial blob removed; a change after the copy completes is not detected, and the staged blob holds the bytes that were hashed. The path is checked (as for `stage_bytes`) before the file is read, and the commit of a streamed file keeps the write order above.
- When the head moved past the base, the commit rebases the change set onto the new head if no intervening version changed a staged path (for a staged tree or a revert, which state the whole working state, any path), and otherwise refuses with `ChangeError::Conflict` (paths named) without publishing and keeps the staging area. It retries at most `MAX_REBASES` (16) times.
- Version-bound logical files ([OCFL-S-024](./resources/srs.md), IO-1.5): `commit_with`, `revert_with` and `reinstate_with` take an optional `write::VersionBoundFiles` function (any closure `Fn(&BoundContext) -> Result<BTreeMap<String, Vec<u8>>, String>`). `ObjectWriter::commit_bound` calls it after reserving `vN` and before writing any `vN` byte, with the reserved version, the `created` time the inventory will carry, the logical states before and after, and whether the reservation took over a held lease; its files (at most `MAX_BOUND_FILES`, each at most `MAX_PUT_BYTES` and together at most `MAX_BOUND_BYTES` (16 MiB), never a path the version already holds) are digested and written like staged content, a rebase calls it again with the new version name, and a failure (`CommitError::BoundFiles`) publishes nothing. `commit_bound_only` publishes a version whose only change is those files (an empty set is refused; staged changes wait for a later commit). The engine gives the files no meaning; FileSquid uses them for each version's PROV-O record (ADR 040).
- A head without its version inventory (W010) stays refused (`ChangeError::Commit(CommitError::MissingVersionInventory)`); the change model never repairs it ([OCFL-S-020](./resources/srs.md)). The writer-fencing gap above is unchanged ([OCFL-S-018](./resources/srs.md) "Known gap").

## UI view API

The `view` module holds the calls `filesquid-api` routes to every UI to browse and edit an object like a drive ([OCFL-S-012](./resources/srs.md), [ADR 028](../../../../resources/architecture/028-filesquid-ui-packages-and-panel-composition.md), [ADR 030](../../../../resources/architecture/030-filesquid-api-and-transports.md)). It returns storage facts only (C-055): nothing reads embedded or descriptive metadata, and the type hint is the lowercase extension. Listings, details, version records, histories and fixity reports have JSON forms (`to_json`, `versions_json`, `history_json`); `read_range` returns raw bytes and the writes return the change model's `CommitReceipt`.

- Reads take an opened `Object` and a version the caller pins: `list_folder(&object, &version, prefix, cursor, limit)` lists the implied folders, then the files, directly below a logical-path prefix (`""` for the root), at most `MAX_PAGE_ENTRIES` (1,000) per page, with an opaque cursor; each file carries its digest, size (read from the backend), the version that last set its content and that version's `created`. `file_details` adds the content path, the fixity values the inventory records and the last change's `user` and `message`. `file_history` lists the versions that added, changed or deleted a path; `object_versions` lists every version. `read_range` returns at most `MAX_RANGE_BYTES` (8 MiB) for previews and downloads; `check_fixity` reads the stored bytes once and compares them with the manifest digest and each fixity value the engine can compute, reporting a mismatch rather than failing.
- Writes take a `ChangeModel` and publish exactly one version each, through the [change model](#change-model) only: `add_file`, `move_path` and `remove_path` (a file, or a folder with every file below it) and `restore` (files or folders from an earlier version, through `reinstate`). Write arguments are logical paths without a trailing `/`. A write is refused with `ViewError::StagingNotEmpty` while the staging area holds other changes, and leaves them untouched. A write that fails after it has staged clears the staging area only if its index is still the one the write staged, so changes staged by someone else are never deleted. A W010 head stays refused and is never repaired.
- OCFL stores no empty folder, so creating a folder is not a write: the UI keeps it pending until a file is added beneath its prefix, and `list_folder` reports `ViewError::FolderNotFound` for a prefix with no file below it (the root of an empty version is an empty page). A cursor belongs to one listing (object, version and prefix); another listing refuses it.

Run its tests and BDD feature:

```bash

cargo test -p filesquid-ocfl --locked --test integration_view_api
cargo test -p filesquid-ocfl --locked --test features -- --input "view_api_*.feature"
```

## Opaque bytes

The engine stores the content bytes its caller supplies and reads them only as bytes ([OCFL-S-021](./resources/srs.md); [ADR 010](../../../../resources/architecture/010-ocfl-1-1-dual-profile.md), [ADR 023](../../../../resources/architecture/023-filesquid-ocfl-engine-and-parquet.md)). Logical paths are UTF-8 strings stored as given, but they must pass the OCFL 1.1 path rules (E052, E053) like any other; a caller that hides names encodes them to meet those rules. Digests are `sha256` of exactly what was stored, so manifest digest verification (E092) works over ciphertext without a key; fixity block values (E093) are checked the same way. The owner-readable local profile has no transform: the caller stages its plaintext as is. Only the encrypted hosted package is a caller transform, planned for `filesquid-api` (which has no sealing code yet): it seals content and names before it stages them and opens what it streams back. Both profiles use the same `ObjectWriter` and `Object` calls; the engine has no profile, key or encryption type and no encryption dependency. Over sealed bytes the inventory stays structurally readable OCFL 1.1, and the engine and community validators accept the object.

`integration_opaque_bytes` and `opaque_bytes_OCFL-S-021.feature` check this. A test-only keystream transform (not cryptography) seals the 7 content fixtures. The tests check that the engine validator reports zero errors, that the community validators accept the objects when they are installed, and that the caller recovers every version. They also check that no stored key, inventory text or content file shows plaintext (names, object id, `message`, user name and address, or content; `created` stays a plaintext RFC 3339 timestamp, as OCFL requires), and that unchanged sealed bytes are stored once. Other inputs are stored as content and read back byte-identical: every byte value, empty files, bytes that are not UTF-8, OCFL-looking files and a file larger than one 8 MiB chunk.

## Independent recovery

A completed snapshot copies with ordinary tools and recovers without FileSquid or Git ([OCFL-S-022](./resources/srs.md); [PRD RC-010](../../../../resources/prd.md#rc-010-complete-ocfl-preservation-and-independent-recovery)). `integration_independent_recovery` and `independent_recovery_OCFL-S-022.feature` write a snapshot with the engine's writer (a sha256 object with two versions, photos, `.xmp` sidecars and a note, and a sha512 object), copy the storage root with `std::fs` only, and then check the copy three ways: the engine opens, validates and enumerates it like the source; an independent reader that uses only `serde_json` and SHA-2 rebuilds every logical file of every version, the folders and the sidecar pairs; and a community validator accepts it when one is installed. Opening, enumerating, validating and reading leave source and copy byte-identical. A changed byte of a preserved original is reported E092 and the verified read stops with E092; a changed root inventory is E060 and refused on open; a forged inventory with a recomputed sidecar is still E092; an edited earlier-version inventory is E060. A copy whose head has no version inventory (W010) stays refused for commits and is never repaired by the copy or any read, because only the owner-consented repair ([OCFL-S-020](./resources/srs.md)) adds that file.
