# Implementation Plan: api (`filesquid-api`)

`filesquid-api` is the **single FileSquid API** for every feature and every distribution: a transport-agnostic router owned here, a versioned contract with generated TypeScript types, authentication and authorisation, jobs and events, and the distribution manifest. Both hosts mount it: `filesquid-desktop` through a Tauri custom URI scheme and `filesquid-server` over HTTP plus an event channel; the roadmap browser host runs its `wasm32` build ([ADR 030](../../../../../resources/architecture/030-filesquid-api-and-transports.md)). UIs call this API and nothing else.

It is also FileSquid's **application layer**. The client logic once planned as the separate private-client library (`apps/client`, the `CL` rows below) lives here: catalog, search, replica and the FileSquid OCFL application profile (file objects, collection snapshots, dual-profile encryption), built against storage backends injected by the host ([ADR 001](../../../../../resources/architecture/001-shared-rust-core-with-tauri-and-axum-hosts.md), [ADR 025](../../../../../resources/architecture/025-client-side-filesquid-engines.md), [ADR 029](../../../../../resources/architecture/029-filesquid-unified-product-and-distributions.md)). It links `filesquid-core`, `filesquid-ocfl`, `filesquid-metadata` and `filesquid-c2pa`. It MUST NOT link Tauri host APIs, libvips, FFmpeg or a SQLite driver and MUST NOT do storage I/O itself (`std::fs`, network clients) ([API-S-006](./srs.md)). The ciphertext-only hosted service MUST NOT link its read paths over private plaintext ([ADR 032](../../../../../resources/architecture/032-hosting-and-privacy-model.md)). Module SRS: [srs.md](./srs.md). Background on the former plan: [client-README.md](./client-README.md).

Cargo commands run from `apps/filesquid/` with `-p filesquid-api` (`cargo test -p filesquid-api --locked`, rustfmt, Clippy). Allure/JUnit under `tests/allure-results/`. Global sequence: [implementation-plan.md](../../../../../resources/implementation-plan.md).
