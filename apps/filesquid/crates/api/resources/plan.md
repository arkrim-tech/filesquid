# Implementation Plan: api (`filesquid-api`)

`filesquid-api` is the **single FileSquid API** for every feature and every distribution: a transport-agnostic router owned here, a versioned contract with generated TypeScript types, authentication and authorisation, jobs and events, and the distribution manifest. Both hosts mount it: `filesquid-desktop` through a Tauri custom URI scheme and `filesquid-server` over HTTP plus an event channel; the roadmap browser host runs its `wasm32` build ([ADR 030](../../../../../resources/architecture/030-filesquid-api-and-transports.md)). UIs call this API and nothing else.

It is also FileSquid's **application layer**. The client logic once planned as the separate private-client library (`apps/client`, the `CL` rows below) lives here: catalog, search, replica and the FileSquid OCFL application profile (file objects, collection snapshots, dual-profile encryption), built against storage backends injected by the host ([ADR 001](../../../../../resources/architecture/001-shared-rust-core-with-tauri-and-axum-hosts.md), [ADR 025](../../../../../resources/architecture/025-client-side-filesquid-engines.md), [ADR 029](../../../../../resources/architecture/029-filesquid-unified-product-and-distributions.md)). It links `filesquid-core`, `filesquid-ocfl`, `filesquid-metadata` and `filesquid-c2pa`. It MUST NOT link Tauri host APIs, libvips, FFmpeg or a SQLite driver and MUST NOT do storage I/O itself (`std::fs`, network clients) ([API-S-006](./srs.md)). The ciphertext-only hosted service MUST NOT link its read paths over private plaintext ([ADR 032](../../../../../resources/architecture/032-hosting-and-privacy-model.md)). Module SRS: [srs.md](./srs.md). Background on the former plan: [client-README.md](./client-README.md).

Cargo commands run from `apps/filesquid/` with `-p filesquid-api` (`cargo test -p filesquid-api --locked`, rustfmt, Clippy). Allure/JUnit under `tests/allure-results/`. Global sequence: [implementation-plan.md](../../../../../resources/implementation-plan.md).

- [ ] **Task API-F1.3: File operation routes**
  - **Description:** Routes for folder listing by logical-path prefix with cursor paging, file details, version history, ranged content reads, upload, create folder, rename or move, remove and restore. A new empty folder stays UI-pending and is persisted only when a file is added beneath its prefix (OCFL cannot store an empty folder). Every other content or organisation change commits one OCFL version through the `filesquid-ocfl` change model (IO-1.2); there is no second write path. Responses carry opaque handles, never filesystem paths. Content handles for media elements ([API-S-018](./srs.md), [ADR 030](../../../../../resources/architecture/030-filesquid-api-and-transports.md) Decision 5, owner decision 2026-10-18): `POST /api/v1/content-handles` mints, for a Bearer caller authorised exactly like the ranged content read of that file version, a 256-bit random handle for one object, version and logical path (SHA-256 digest kept in memory only; at most 1,024 live per credential, least recently used evicted); `GET` and `HEAD /api/v1/content/<handle>` serve that version's bytes with the same `Range` handling and caps as the ranged read, on the desktop scheme and on `filesquid-server`; idle timeout 300 s, sliding from mint and each accepted request start, absolute lifetime 3,600 s, checked only at request start; invalid when the issuing credential ends; one identical denial (403 `forbidden`, `invalid_credentials`) for any unusable handle, with no file read first; `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox` on every answer; never logged or journaled (`api.content_handle.issued` carries no handle; redaction tests). - [ ] **Task API-F1.11: Navigation listing route**
  - **Description:** Follow-up to CL-0.2, which defines the library, collection and virtual-collection queries but no route (owner-approved 2026-10-18; it does not change CL-0.2 or its pull request). `GET /api/v1/navigation` lists one level of the navigation tree per [API-S-021](./srs.md): without `node`, the connected host's repository; with `node`, its children (a repository's libraries; a library's collections, virtual collections and the folders implied by its unfiled files; a collection's folders; a folder's subfolders; nothing under a virtual collection; never files). Folders implied only by hidden or deleted files are left out. Permission filtering happens before paging; `has_children` counts readable children only; unknown and unreadable nodes get the same `not_found`. A `navigation.change` event names the changed parents (1 to 64 handles, or `all` `true`), filtered per subscriber. Update the contract and regenerate the UI types.
