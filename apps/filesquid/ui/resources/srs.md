# `@filesquid/ui` SRS (scaffold)

FileSquid's default distribution and component library. Parents: [SRS-F-062](../../../../resources/srs.md#srs-f-062-drive-style-views-sorting-selection-and-layout-preferences)–[SRS-F-066](../../../../resources/srs.md#srs-f-066-file-and-folder-sharing-roles-links-and-shares-view) (UI-S-006–010), [SRS-F-055](../../../../resources/srs.md#srs-f-055-default-ui-and-panel-composition), [SRS-F-058](../../../../resources/srs.md#srs-f-058-white-label-distributions), [SRS-UI-007](../../../../resources/srs.md#srs-ui-007-light-and-dark-themes). UI-S-015 (brand slots, theme control and contrast contract) traces to SRS-UI-007 and SRS-F-058. UI-S-016 (accessibility contracts) traces to [SRS-NFR-006](../../../../resources/srs.md#srs-nfr-006-accessibility-and-usability). UI-S-017 (navigation preferences) traces to [SRS-F-004](../../../../resources/srs.md#srs-f-004-collections-folders-and-navigation) and UI-S-018 (host privacy indicator data) to [SRS-F-057](../../../../resources/srs.md#srs-f-057-desktop-and-server-hosts) and [SRS-F-059](../../../../resources/srs.md#srs-f-059-hosted-encrypted-backup-and-sync-service). UI-S-014 (client authorisation) traces to [SRS-F-056](../../../../resources/srs.md#srs-f-056-single-filesquid-api), [API-S-004](../../crates/api/resources/srs.md) and, for content handles, [API-S-018](../../crates/api/resources/srs.md). UI-S-011, UI-S-012 and UI-S-013 moved here from the former `apps/frontend` SRS (now the ImageSquid SRS), where they were FE-S-001, FE-S-002 and FE-S-004. UI-S-024 to UI-S-034 record the composition of the active mockup suite, [v3](../../../../resources/ui-mockups/v3/README.md) (owner decision 2026-10-22, verbatim: "yes, make v3 the active suite in that PR"), and trace to the PRD rows named in their last cell; the mockup files they cite are requirement sources ([mockups README](../../../../resources/ui-mockups/README.md)).

| UI-S-023 Client event delivery. The UI MUST forward its console warnings and errors to `POST /api/v1/client-events` (API-S-030), each with a client event ID (UUID v4) that the event keeps for life, so every resend after a lost acknowledgement and every delivery on the next open carries its original ID and the route's once-per-ID journaling (API-S-030) de-duplicates it, through a bounded in-memory queue of at most 10,000 events: it sends batches of at most 20 events and 16 KiB, at most 60 requests a minute, and keeps every sent batch queued until the route acknowledges it. When the in-memory queue is full, further events MUST spill, in order, into the page's IndexedDB store, within a storage budget of 50 MiB for the origin, and no event is discarded while storage accepts writes; spilled events move back into the queue, oldest first, as it drains. While storage accepts writes, every queued event MUST also be written to IndexedDB as it is queued and removed when the route acknowledges it, so a crash or force-quit that skips `pagehide` loses no event whose write had committed. When the page closes (`pagehide`), every event still queued in memory or unacknowledged MUST be persisted to IndexedDB, and the next time FileSquid opens it MUST deliver the persisted events, oldest first and each as its own journal entry, before new events. Every spilled or persisted event MUST be stored with the host it was raised against and the opaque ID of the authenticated principal of that session (the desktop owner, or the server account); the UI MUST send a stored event only under a credential of that same host and principal, and MUST hold the events of any other principal, untouched, until that principal signs in again on this device, so no event is ever replayed under another user's credential. After a `429`, a `401` or `403`, a `5xx` or a network failure it retries the same events with exponential backoff (from 1 second, doubling, at most 60 seconds between attempts, never sooner than `Retry-After`) for as long as the page is open. A `400` refusal of a batch MUST NOT be retried as it is: the UI resends each of its events alone, and an event the route refuses on its own is removed from the queue and replaced by one `ui.console.error` event with the error code `client_event_refused` and the refused event's component, so one bad event cannot block the queue. Rate limits MUST only delay events, never merge them: a request MAY carry several events, but each delivered event MUST become its own journal entry. The one unavoidable gap is storage that is unavailable or cleared: when IndexedDB is unavailable (for example in a private window) or refuses a write (quota refused or the 50 MiB budget reached), the UI MUST fall back to the in-memory queue, MUST count every event it could not keep, and at page close MUST send one `ui.console.overflow` event, carrying its own client event ID and `count`, an integer from 1 to 1,000,000 (never 0, and capped at 1,000,000), with no error code or other IDs (API-S-030), as a keep-alive request ( with no storage to persist the count, a failed request loses it uncounted, part of the same gap); events lost because the person cleared the site's data, and an event whose IndexedDB write had not committed when the page ended without `pagehide`, cannot be counted. This gap is recorded in `logging-enforce.md` (owner decision 2026-10-19). Events carry only the level, a fixed component identifier, an error code and opaque IDs, never message text, URLs, file names or stack traces. | [PRD F-061](../../../../resources/prd.md#f-061-activity-journal-and-live-health-monitoring), [SRS-F-061](../../../../resources/srs.md#srs-f-061-activity-journal-and-live-health-monitoring), [ADR 033](../../../../resources/architecture/033-activity-journal-and-live-health-monitoring.md) |
