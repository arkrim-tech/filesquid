## Conflict 1: the dark surface of the bar, the zoom chip and the previous and next controls

1. **Conflict description.** The plan row puts the top bar and the zoom chip on `--fs-surface-card` (`#ffffff` / `#1c1c1c`). The dark mockup fills them, and the two round controls, with `#141414`, which is `--fs-surface` dark (the shell header's colour), not `--fs-surface-card`. In light both tokens are `#ffffff`, so only dark differs.
2. **PRD/SRS reference.** Plan row UI-F2.19: "the 52 px top bar on --fs-surface-card with a 1 px --fs-outline bottom line"; "the zoom chip under the media (36 px pill, radius 18 px, --fs-surface-card, 1 px --fs-outline)". UI-S-024: "`--fs-surface` page `#ffffff` / `#141414`; `--fs-surface-card` (new) sidebar, panels, cards, inputs and secondary buttons `#ffffff` / `#1c1c1c`". Dark SVG: `<rect x="240" y="89" width="880" height="52" fill="#141414"/>`, `<rect x="550" y="624" width="260" height="36" rx="18" fill="#141414" stroke="#2A2A2A" stroke-width="1"/>`, `<circle cx="284" cy="391" r="20" fill="#141414" stroke="#2A2A2A" stroke-width="1"/>`.
3. **ADR reference.** [ADR 031](../../../../../resources/architecture/031-vanilla-typescript-ui-and-white-label-theming.md): colours only through tokens, so the choice is which token, not a hex value. SRS-UI-007 exempts `#6a6a6a` on both `#141414` and `#1c1c1c`, so either choice passes the contrast test for the muted position text and the loading text.
4. **Recommended resolution.** Keep the plan row's `--fs-surface-card` (built) and redraw the three dark fills of mockup 22 as `#1C1C1C`; or switch the three to `--fs-surface` (one token each in `file-browser-frame.ts` and `fs-file-preview.ts`) and change the plan row and the UI-S-031 wording. Artifacts to update for the first: both mockup 22 SVGs (dark only); for the second: the plan row, `file-browser-frame.ts`, `fs-file-preview.ts`, `tests/e2e/preview/preview-top-bar.spec.ts`.
5. **Impact assessment.** Nothing breaks. In dark the bar is 8 levels of grey lighter than the mockup draws it.

## Conflict 2: the zoom-out and zoom-in buttons in the chip

1. **Conflict description.** Mockup 22 draws the chip 260 px wide with a zoom-out icon (`translate(566 634)`, a magnifier with a minus) before "Fit · 38%" and a zoom-in icon (`translate(660 634)`, a magnifier with a plus) after it. The plan row and UI-S-031 exclude zooming beyond Fit.
2. **PRD/SRS reference.** Plan row: "Zooming beyond Fit is not part of UI-S-031 or of this row"; Agent Prompt: "Do not build the filmstrip … or zooming beyond Fit". UI-S-031: "a zoom chip 'Fit · {percent}%' with 'Loading full size' while it loads".
3. **ADR reference.** [holistic-ui.md](../../../../../.agents/rules/holistic-ui.md): no throwaway scaffolding; a disabled zoom button would be one.
4. **Recommended resolution.** Built: the chip holds "Fit · {percent}%" and, while loading, "Loading full size" with its bar, and no zoom buttons, so the chip is as wide as its text (its height, radius, colours and place under the media match the mockup; its width does not, and the Playwright test does not assert 260 px). Either the owner confirms this and mockup 22 drops the two icons, or a later task schedules zooming and adds them. Artifacts to update: both mockup 22 SVGs, or a new plan row with the zoom steps.
5. **Impact assessment.** None for the MVP: the chip states the scale; it cannot change it.

## Conflict 3: no route tells the file browser which collection it shows

1. **Conflict description.** The bar shows "the collection the shown file is in (… taken from the browser's current location and its breadcrumb trail, never guessed, and left out when the location names no collection)". No route gives the file browser a collection: `#/files/<library>/<object>/<folder>` names an object and a folder, the Drive view opens a file at `#/files/<library>/<object>/original`, and the browser's breadcrumb trail starts at "All files" (`fileRoot`), which is not a collection. So in the running app the collection is always left out.
2. **PRD/SRS reference.** Plan row UI-F2.19 **Top bar** (quoted above); UI-S-031 "a bar with the collection, the badge, the display name".
3. **ADR reference.** UI-F2.17 (plan row): "Left for this task: a producer of `FileLocation.collection_id` (no route or tree node supplies one yet …)". UI-S-019: names shown come from the API.
4. **Recommended resolution.** Built: `FileLocation` gains the optional `collection_name` (the collection's name as the API gave it to the route); the bar shows it when present and leaves it out otherwise, never guessing from a path. The task that produces `collection_id` (UI-F2.17, through `GET /api/v1/navigation/destination` and the navigation node's title) also sets `collection_name`. Artifacts to update: the UI-F2.17 plan row (one line).
5. **Impact assessment.** Until then the bar shows the back control, the badge, the name and the position, without the collection. No wrong name is shown.
