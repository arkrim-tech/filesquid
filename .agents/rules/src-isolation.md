# Source Directory Isolation Rule

In this monorepo architecture (enforced via [`workspace-boundaries.md`](./workspace-boundaries.md)), an application or service resides within a dedicated workspace directory (e.g., `apps/filesquid/`, `apps/imagesquid/`, or `apps/my_app/`).

The primary execution directory **inside** each of these workspaces must contain the complete application codebase required to build and deploy that specific project. The primary design principle for any workspace's execution directory is to be **standalone and exportable**.

## Stack-Specific Execution Directories
- **For Python Stacks:** The execution directory is strictly `app/` (e.g., `apps/backend/app/`), replacing outdated `src/` patterns.
- **For JavaScript/TypeScript Stacks:** The execution directory is strictly `src/` (e.g., `apps/filesquid/ui/src/`, `apps/imagesquid/src/`) as dictated by modern bundlers like Vite or Next.
- **For BEAM/Elixir Stacks:** The execution directory is strictly `lib/` (e.g., `apps/my_app/lib/`) as dictated by OTP.
- **For PHP Stacks:** The execution directory is strictly `src/` for namespaced PHP (e.g., `apps/c2papress-audit/src/`) via Composer PSR-4. WordPress requires the main plugin bootstrap file at the plugin workspace root (e.g., `c2papress-audit.php`); that file is bootstrap only. Enqueued JavaScript lives in `assets/js/` inside the same plugin workspace, not a separate `apps/frontend`.
- **For Rust Stacks:** The execution directory is strictly `src/` for each Cargo crate (e.g., `apps/filesquid/crates/core/src/`, `apps/filesquid/crates/server/src/`). For the Tauri 2 host, the crate root is `apps/filesquid/crates/desktop/` and the execution directory is `apps/filesquid/crates/desktop/src/`. Do not put domain logic or native I/O in the desktop or server host crates: domain logic belongs in a module crate behind `filesquid-api`, and native I/O (SQLite, filesystem checks, native workers) belongs in `filesquid-native`.

## Strict Isolation Requirements

1. **Self-Contained Execution:** All environment configuration files and dependency manifests (like `package.json`, `mix.exs`, `requirements.txt`, `composer.json`, `Cargo.toml`, or `rust-toolchain.toml`) MUST reside at the root of the workspace directory (e.g. `apps/imagesquid/`, `apps/filesquid/ui/`), or, for a product-local Cargo workspace, at the workspace root (`apps/filesquid/Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`) and at each crate root (`apps/filesquid/crates/<module>/Cargo.toml`), while the actual executable application source code MUST be strictly placed inside its designated execution folder (`src/`, `app/`, or `lib/`).
2. **Zero External Workspace Dependencies:** Code within a workspace's execution directory MUST NOT import from, rely on, or hard-link reference any files outside of its own workspace boundary. You should be able to copy or export an entire workspace folder (e.g., `apps/my_app/`) from this repository and have a fully functional, self-contained application.
   - *BEAM/Elixir Exception Handling*: In Elixir architectures, apps within `apps/` may sometimes rely on each other via `in_umbrella: true` or local `path: "../my_other_app"` directives in their `mix.exs`. To maintain the exportability mandate, `@AGENTS.md` MUST prefer sourcing shared dependencies via verified Hex packages or Git-referenced repositories whenever possible. Local path dependencies should exclusively be used only if the applications are truly inseparable parts of the exact same domain logic.
   - *PHP Exception Handling*: Plugins MAY path-depend on a shared Composer library (e.g., `apps/c2papress-shared/`) during development. Each **shippable zip** MUST vendor or copy that code so the plugin runs on WordPress alone. WordPress.org MUST NOT require a sibling path package at runtime.
   - *Rust Exception Handling*: Crates inside one product-local Cargo workspace (`apps/filesquid/crates/*`) MAY path-depend on each other. Host crates (`filesquid-server`, `filesquid-desktop`) depend on `filesquid-api`. `filesquid-desktop` depends on `filesquid-native` (with `desktop`); `filesquid-server` MAY depend on it with default features only. `filesquid-api` depends on the module crates (`filesquid-core`, `filesquid-ocfl`, `filesquid-metadata`, `filesquid-c2pa`) and MUST NOT depend on `filesquid-native`. `filesquid-native` holds host-side native I/O (SQLite storage, data-directory checks, `HostMonitor`, and later the OCFL coordinator and media workers). Its desktop-only parts sit behind the `desktop` Cargo feature, which `filesquid-server` MUST NOT enable ([ADR 033](../../resources/architecture/033-activity-journal-and-live-health-monitoring.md) amendment). WASM builds and the ciphertext-only hosted service MUST NOT link it. Module crates MUST NOT depend on `filesquid-native`. Module crates MUST NOT depend on Axum, Tokio-net, or `tauri`, and MUST NOT take a default dependency on another module crate (the current unconditional `filesquid-metadata` → `filesquid-ocfl` dependency is a known gap, scheduled to become the optional `ocfl` feature). Each module crate MUST still build and test alone (`cargo test -p <crate>`). The whole `apps/filesquid/` directory MUST stay extractable to its own repository: no path dependency may point outside it. Do not introduce a root `Cargo.toml` workspace to share code.
   - *TypeScript Exception Handling*: A white-label distribution (e.g., `apps/imagesquid/`) MAY depend on `@filesquid/ui` by relative path (`file:../filesquid/ui`) during development. A release build MUST depend on a published, version-pinned `@filesquid/ui`. A distribution contains no Rust and no server code.
3. **No Global Dev Tooling in Execution Folders:** Monorepo-level management tools, global architecture decision records, AI agent configuration (`.agents`, `docs`, etc.), and global testing artifacts MUST be kept outside individual workspaces. The execution directory (`app/`, `src/`, or `lib/`) of any app or service must remain deployment-ready and unpolluted by global meta-files.
