Backup after the MVP

Backup is the product that follows the FileSquid MVP. People do their daily work in a Drive. OCFL stays behind that Drive.

This file holds two things. The field prospectus is reproduced in full, because its backup rules are product requirements. The design half says how those rules become filesquid-backup, and in what order to build them once the MVP is finished.

Source

The field pipeline

The source is FileSquid field media pipeline, technical prospectus v1, 29 October 2026. Its claim is narrow. Large files move from places with poor wifi and unreliable power into three independent archives. Encryption runs on the device before any byte leaves. Nodes, archives and relays see ciphertext.

Prospectus · 1

Backup is not sync

Backup is a point-in-time copy kept separately so you can go back. Sync keeps two or more live copies the same so you can continue from anywhere.

The decisive difference is what happens to a mistake. Delete a file in a synced folder and it is deleted everywhere within seconds. Delete it in a backed-up folder and yesterday’s snapshot still has it. Sync propagates. Backup preserves. A system that needs both availability and recovery needs both layers.

Backup

  • One-way, source to store
  • Scheduled snapshots, versioned, often immutable
  • Goal: recovery from deletion, ransomware or a dead disk
  • Hard problem: retention and restore testing
  • Verified by restoring

Sync

  • Two-way or many-way
  • Continuous; latest state wins
  • Goal: one working set on every device
  • Hard problem: conflicts when two sides change the same thing
  • Verified by comparing

Common open-source tools

A sane baseline pairs one of each: Syncthing between laptop and phone for working files, restic to a separate location nightly, following the 3-2-1 rule of three copies, two media types, one off-site.

Prospectus · 2

Conflicts and CRDTs

File-level sync resolves a conflict by picking a winner or duplicating the file. A conflict-free replicated data type resolves it inside the data, so every replica converges without a referee.

A CRDT represents each edit as an operation that commutes with every other. Two devices can edit offline for a week, exchange their logs in any order, and arrive at identical documents. This is the basis of local-first software (Kleppmann, Wiggins, van Hardenberg and McGranaghan, 2019), where the user’s device holds the primary copy and servers are optional.

Automerge

Automerge provides fast implementations of several CRDTs (maps, lists, text, counters), a compact compression format, and a sync protocol that sends a peer only the operations it lacks. The core is Rust, compiled to WebAssembly for the JavaScript package, with C bindings that have spawned further ports, including an R package on CRAN. The protocol’s thrift suits intermittent connections.

Trade-offs
  • Metadata grows with history. Deletions leave tombstones.
  • Merges are consistent, and they are not a judgement. Two people editing one sentence get an interleaving.
  • Large binaries do not belong in a CRDT. The CRDT holds the index and metadata. A blob store holds the bytes.
LibraryLanguageNotes
AutomergeRust, JS, CRich history, sync protocol, local-first focus
YjsJSVery fast, widely used in collaborative editors
LoroRust, JSNewer, focused on performance and rich text
Diamond TypesRustText CRDT optimised for speed

Prospectus · 3

Peer-to-peer transport

CRDTs decide what to merge. Something still has to move bytes between devices that sit behind NAT, on cellular, or off the public internet.

Iroh is a Rust library for establishing the most direct QUIC connection possible between two devices, addressed by public key rather than IP. It reached 1.0 and is dual-licensed MIT and Apache 2.0.

  • Identity is the key. Each endpoint has an Ed25519 keypair. The public key is both the address and the TLS certificate subject, so no certificate authority is involved.
  • QUIC over UDP gives encryption, multiplexed streams and connection migration. A phone moving from wifi to cellular keeps its connection.
  • Hole punching gets through most NATs automatically.
  • Relay fallback carries traffic when a direct connection fails. Relays see only ciphertext. The relay server is open source.
  • Discovery resolves a key to current addresses through DNS or Pkarr. n0’s public infrastructure can be swapped for your own.
CratePurposeRole in this design
iroh-blobsContent-addressed transfer with BLAKE3, verified streaming, resumptionMoving backup chunks between archive nodes
iroh-gossipPublish-subscribe overlayAnnouncing “I have these hashes”
iroh-docsEventually consistent key-value storeReplicating small manifests

Automerge over Iroh is a serverless sync stack: CRDT documents for mutable state, blobs for large files, gossip for discovery, QUIC for transport. It gives offline-capable multi-device sync with no server. It still gives no backup. A corrupted or maliciously edited document converges everywhere. Comparable stacks are libp2p (IPFS), Hyperswarm (Holepunch) and Syncthing’s own protocol.

Prospectus · 4

Syncing the backups

Replicating a backup repository is a third layer. Here sync becomes safe again, because what is being synced is already immutable and versioned.

Why it works

A restic, Borg or Kopia repository is content-addressed. Chunks are named by their hash, and snapshot manifests point at chunks. Files are only ever added, never modified in place. Deletion happens only through an explicit prune. Two copies with different sets of objects are reconciled by taking the union. That is a grow-only set, the simplest CRDT, so replication is conflict-free by construction.

ToolMechanism
resticrestic copy between repositories (different keys allowed); rclone backend to any object store
BorgBackuprsync the repository directory; borg transfer; borgmatic targets several repositories
Kopiakopia repository sync-to mirrors a repository to another backend
ZFS, btrfszfs send piped to zfs recv: incremental snapshot streams at the filesystem level
SyncthingSend-only folder carrying a repository to a remote machine

Hazards

  • Prune propagation. Prune the primary, sync, and the deletion propagates. Use object lock or immutable buckets, or a sync mode that never deletes on the mirror.
  • Partial sync. A half-copied manifest references missing chunks. restic check detects it. Writing chunks before manifests keeps a partial copy consistent.
  • Ransomware. An attacker with write access to the primary corrupts it, and sync carries the corruption. Pull-based replication and append-only modes (Borg --append-only, restic rest-server --append-only) break the chain.
  • Lock files. Sync only when no backup run is in progress.
Where Iroh fits

A repository is a set of BLAKE3-addressed blobs plus a small manifest, which is exactly what iroh-blobs transfers. Archive nodes gossip the hashes they hold and fetch the difference from any peer: a serverless 3-2-1 across sites behind NAT. Retention is the one operation that needs a policy rather than a merge, which is why pruning is the hard part of every such system. git-annex and Perkeep already work this way.

What a PWA can do

  • iOS Safari has no Background Sync. Uploads progress only while the PWA is open, so the field guidance is “open the app when you have signal.”
  • Android Chrome supports Background Sync and Background Fetch, so queued uploads continue after the app is closed.
  • Service workers and IndexedDB work on both, which is enough for durable queues and resume.

On Garage

Garage is an open-source S3-compatible store built by Deuxfleurs for geo-distributed clusters on cheap, flaky hardware. Running it across sites with replication factor 3 gives object-level replication for free. Snapshots are still required, because replication propagates deletions and corruption instantly.

Prospectus · 7

Resumable upload

The PWA keeps uploading until the server confirms the last byte, however many times the connection, the app or the phone dies in between.

The protocol is tus, with tus-js-client in the browser and tusd on the node. The client never guesses what arrived. After any interruption it asks the server for its offset and continues from there.

StepWhoWhat
1User actionEncrypt, hash, and hand the blob to the queue
2Service worker and IndexedDBSave the handle and the hash before any network call
3Client to tusdPOST with Upload-Length and the hash. The 201 returns an upload URL, saved to IndexedDB
4Client to tusdPATCH 2 MB chunks from offset 0, then from 2 MB
5InterruptionWifi drops, the app is killed, or the phone dies. The queue survives on disk
6ReopenRead the queue from IndexedDB. HEAD the upload URL. The server answers Upload-Offset, for example 4 MB
7Client to tusdPATCH from that offset until the end. 204 when offset equals length and the hash matches
8QueueMark complete and remove the item

One interruption is shown. The same HEAD-then-PATCH loop handles any number.

Design rules

  • Persist first, upload second. The moment the user picks media, the encrypted blob, its hash and the upload URL are written to IndexedDB. Nothing is held only in memory.
  • Small chunks. 1 to 4 MB on poor wifi so each round trip has a chance to complete. The size can adapt to measured throughput.
  • Hash the ciphertext. The node verifies the BLAKE3 hash on completion and rejects mismatches. The same hash is the deduplication key and the content address for later layers.
  • Retry with backoff and resume on every app open and every online event. On Android, also through Background Sync.
  • Idempotent finish. A completed upload the client failed to record shows up on the next HEAD, when offset equals length, and is marked done.
  • Minimal metadata. tus headers carry only hash and size. Filename, timestamps and location travel inside the encrypted payload.

Prospectus · 8

End-to-end encryption

The field worker’s phone and the authorised viewer are the two ends. Everything between them, including FileSquid’s own nodes, archives and relays, sees only ciphertext.

Encryption scheme

  • age is the primitive: X25519 per-recipient key wrapping, streaming ChaCha20-Poly1305 for large files, several recipients in one envelope. A TypeScript implementation runs in the PWA. The CLI serves the viewing side.
  • Each media file gets a random file key, wrapped for every recipient. Adding a receiver later means re-wrapping file keys, not re-encrypting media.
  • The sidecar (filename, timestamp, GPS, notes) is a separate small age blob. The server sees an opaque id, a size and an upload time.

Key custody

  • Recipient public keys are baked into the PWA build or fetched from a signed manifest with a pinned fingerprint, so a hostile server cannot substitute its own key.
  • Receiver private keys live only on receiver devices, ideally hardware-backed. age has YubiKey and FIDO2 plugins. They never sit on a node or an archive.
  • Each phone generates its own keypair on first run and signs every upload. Receivers verify which device captured what. A lost phone’s key goes on a revocation list in the manifest.
  • A lost phone holds no decryption keys. Pending uploads are ciphertext at rest in IndexedDB. The worst case is “we lost the files not yet uploaded”, never “the adversary can read them”. WebCrypto non-extractable keys and a device PIN protect the sender key too.

How it meets the other layers

  • Hash the ciphertext for tus resume and deduplication. The server can verify it. Put the plaintext hash inside the encrypted sidecar for receivers.
  • Deduplication across identical captures is lost, since a random file key yields different ciphertext. The prospectus accepts that for field media. Convergent encryption would restore it at the cost of leaking “same file” to the server.
  • restic’s encryption becomes a second layer around the first. The repository key protects integrity and structure. The age key protects content.
  • Iroh’s transport encryption is a third layer. It does not add content confidentiality. It helps metadata hygiene. Who talks to whom is still visible to a relay.
  • The receiver app pulls ciphertext from an archive, decrypts locally, and never uploads plaintext. Thumbnails are generated on the receiver, not the server. A signed audit log records who decrypted what.
What end-to-end encryption does not solve
  • Traffic analysis: upload sizes and timings from a location. Pad sizes or batch uploads if that is in the threat model.
  • A phone compromised before encryption. No scheme helps. This is device hygiene.
  • Legal compulsion of a receiver who holds a key.

Design · 1 · owner decision, 29 October 2026

Backup is the product

Correction

An earlier draft of this report said the prospectus should stay a reference and should not become a second product beside the OCFL library. That sentence is withdrawn. Backup is the primary product. OCFL is a value underneath it.

Adding backup is the most immediate priority after the MVP is finished. Task FS-3.9 closes the MVP. Backup work starts then. People manage files every day in a Drive: folders, files, search, and versions they can see and restore. OCFL compliance and the preservation layout stay behind that Drive. They are how a recovery point remains readable and how a library can leave the service. They are not the thing the owner operates, and they are not a reason to ship backup later.

The field prospectus supplies the product’s threat model, its resumable upload, the split between backup and sync, and the rule that a backup is real only after a restore. Those are requirements of filesquid-backup. The phone PWA, age, restic, and a field node are not the interface. The Drive is.

Phase F4 in resources/implementation-plan.md is still the named body of work: encrypted backup and sync at *.filesquid.tech, requirements F-029 through F-032, F-042 and F-059, architecture ADR 004, ADR 009, ADR 010, ADR 012 and ADR 032. There is no separate filesquid-backup crate. The product is this work, moved to the front of the queue.

The product vision, the PRD, the SRS, the architecture document, ADR 029, the implementation plan and the checklist now record the same order. Backup follows Task FS-3.9 and precedes Task FS-3.5. The Drive is the interface. OCFL stays behind it. Phase F4 is the Backup section of the checklist, between the MVP and release 1. Release-1 work that backup leaves for later, including Linux and Windows installers, virtual exhibits and the activity stream, waits until Task FS-4.2 is checked.

The same decision is written out as a product canvas in FileSquid backup product vision. That note stays under C-025 and ADR 029. Its local U-numbers are reading aids for this release. They are not allocated into the PRD.

The MVP Drive is the working library. Trash and visible version history protect against a mistake on that disk. F-031 already says that history is not a disaster-recovery service. Backup adds retained recovery points that survive a deleted file, a bad sync, or a dead disk, and it puts those points where the owner can restore them from the Drive.

Design · 3

What filesquid-backup is

filesquid-backup is the product that follows the MVP. The owner lives in the Drive. Backup, restore, and later sync are actions in that Drive. Phase F4 is the implementation, on the desktop and a new hosted binary. OCFL compliance is the storage and the exit path under those actions.

The Drive

Day-to-day file management: folders, files, search, copy, move, and Trash. The MVP library is this Drive on the owner’s disk. Version history the owner can see stays here. The OCFL layout is underneath it. An owner restores a file without learning object identifiers.

Who may upload

The owner of a Drive installation grants another user permission to upload into that Drive by enrolling the user's device public key (Ed25519, ADR 009). That is the permission for network-sensitive uploads: bytes that cross a network the owner does not trust. The uploader encrypts on their device before any byte leaves. The mailbox authorises the key and sees ciphertext. A password is not that permission. Revoking the key stops later uploads. The key can append a recovery point and cannot delete one. Share-link passwords in the release-1 sharing panel are a different control.

Recovery point

A retained generation of that library, stored as an encrypted OCFL profile and shown in the Drive as a point in time the owner can return to. Objects are written first. The manifest is published only when every referenced ciphertext object is present and hashed. Later deletes in the Drive do not remove it.

Hosted copies of recovery points

Each Drive has its own backup. *.filesquid.tech stores ciphertext, issues scoped upload URLs, checks lengths and checksums, and fences publication. It keeps multiple copies of that Drive's recovery points in different geographies. The working Drive is not one of those copies. It does not parse OCFL, render thumbnails, or hold keys. The binary is the one Task SV-F4.1 creates, with the dependency-graph gate. It is not filesquid-server.

Restore

A chosen recovery point, on a clean library directory, unlocked with the recovery phrase, verified on the client. Missing objects are reported. A partial tree is not presented as a library.

Sync, after the first rehearsed restore

Live head replication between devices. Deletes propagate. The UI shows backup and sync as separate facts. The host indicator already has this rule waiting on API-F4.1.

The decisive test

Delete a file, let sync run, restore yesterday’s recovery point, and the file is back. That sentence is the prospectus’s difference between the two layers, turned into an acceptance test.

Design · 4

Decisions to write before implementation

One design record, written as soon as the MVP gate is the predecessor and before backup code, should freeze these points so they are not reinvented inside handlers.

  1. Backup is the product that follows the MVP. The Drive is the interface for daily file work. OCFL compliance stays behind that Drive.
  2. A recovery point is a pinned encrypted OCFL generation. The owner sees a restorable point in time. The owner does not see a restic repository.
  3. Objects first, manifest last. A manifest with missing chunks is not restorable and is not published.
  4. Two hosted credentials: append, and retain. The sync credential cannot delete recovery points.
  5. Object lock, or an equivalent retention floor, on the recovery-point prefix. Providers and regions stay the open operations choice in ADR 012, and that choice names more than one geography.
  6. Resume state lives in the desktop job store. The server’s part offset wins. Completion is idempotent.
  7. Object keys and request metadata are an opaque id, a size and a ciphertext hash. Names, capture timestamps and location stay inside ciphertext. Upload time remains visible service metadata, and the UI says so.
  8. Verification is a ladder: upload receipt, ciphertext hash, a scheduled read of a subset, then a client restore that decrypts and checks the plaintext digest.
  9. The owner of a Drive enrolls a device public key as permission to upload into that Drive. A password is not that permission. The uploader encrypts before the bytes leave. Revoking the key stops later uploads, and the key cannot delete a recovery point.
  10. Each Drive has its own backup, and that backup keeps multiple copies of its recovery points in different geographies. One hosted region plus the laptop is not that design. Further destinations, an air-gapped disk and a paid restore exercise stay F-035.
  11. Paid sync claims wait until one clean-device restore has passed. The plan already says this. The task split below makes it enforceable.
  12. Non-goals for this feature: field PWA capture, age as the content suite, restic as the store, tusd as a product, Iroh, Automerge, server-side thumbnails, convergent encryption, traffic padding, and background phone backup. Postponing backup until after release 1 is also out.

That record is an amendment or a short successor to ADR 010 and ADR 012. The implementation plan, the checklist and ADR 029 already place phase F4 immediately after the MVP and ahead of phase F3R. The record leaves ADR 009 unchanged.

Slice C · Local recovery points

A first cut of DE-5.2 and the encrypted-profile path hook ADR 010 already reserves. Destination: a folder or disk the owner chooses.

No account, and no *.filesquid.tech. Persist the job, encrypt, write objects, publish the manifest, restore onto an empty directory, and check plaintext hashes. This is the prospectus’s layer 2. It can start once the MVP gate has passed, without waiting for Linux installers, virtual exhibits, or the hosted service. Interrupted jobs resume from the checkpoint. A second run of the same point is a no-op.

Slice D · Hosted append-only store

After the MVP gate and the desktop can encrypt. It does not wait for FS-3.5.

Task FS-4.1 (40 hours) creates the hosted binary and the dependency-graph test. Task 0.6 (24 hours) adds accounts, devices, quotas and logs with no private titles. Task IO-5.1 closes the MVP’s known writer-fencing gap (OCFL-S-018) before a second writer shares an S3 root. Task 5.4 (32 hours) publishes per-user encrypted OCFL roots.

Upload uses S3 multipart. tus is optional and terminates into those parts. The append credential fails when it tries to delete or overwrite a locked object. Logs and metrics contain no filenames and no plaintext.

Slice E · Restore drill, before sync is called reliable

Split today’s Task 5.2 (52 hours). The backup half lands with slices C and D.

Status states are selected, queued, uploaded, verified and recoverable. A thumbnail-only copy does not count. Task 5.3 (32 hours) publishes quota, retention and the cancellation download window, with a payment test double. Task 5.5 (16 hours) records one clean-device restore, the silence alarm, the retain-credential prune, and the runbook.

The UI shows backup on and sync off, with ADR 032’s sentence: files are encrypted on the device before upload, and the service never has the keys.

Slice F · Sync

The remainder of Task 5.2.

CO-5.2 conflict and tombstone types, live head replication, rebase or an explicit conflict. The delete-then-sync-then-restore test is the exit criterion. Tombstone compaction must not let a long-offline device resurrect a purged file, and it must not delete a recovery point.

Slice G · Release gate

Task FS-4.2 (12 hours).

Desktop and, when a server library is a backup client, filesquid-server encrypting before upload. Evidence for RC-003 and RC-006: distinct guarantees, restore without the live service catalog, a revoked device, a ciphertext-only dependency graph, and published terms. Evidence also shows an enrolled uploader key that can append and cannot delete a recovery point, and one Drive's recovery points present in more than one geography. No SLA is invented. Paying users still wait on the crypto-protocol audit, named providers and regions in more than one geography, a payment processor, and the GDPR role analysis (F-059).

Task 0.11, the browser commit protocol (12 hours), stays a written protocol in F4 and an implementation in phase F5. Desktop backup does not need the browser writer.

After FS-4.2

  • The encrypted browser host (phase F5), which is the prospectus’s receiver: decrypt locally, and make thumbnails on the device.
  • filesquid-server as a backup client of the same service.
  • A further destination, physical seeding, and inheritance (F-035). The multiple geographies of a Drive's own backup are already in this release.
  • A peer transport, if a user-run third site needs NAT traversal.
  • Phone capture, as a native-app decision. The PWA in the prospectus is not that decision.

Design · 6

What this changes in the current plan

F4’s task list is the right skeleton for the backup product. The implementation plan and the checklist now place it immediately after Task FS-3.9. The prospectus fills in behaviour the skeleton names and does not specify: manifest after objects, a credential that cannot prune, object lock, resume that trusts the server offset, and a restore that is a scheduled proof rather than a demo. Build backup until restore works in the Drive, and only then turn sync on.

The owner’s product is backup, used through the Drive. OCFL, the ADR 009 suite, and the ciphertext-only mailbox stay behind that Drive so a recovery point can be restored and a library can still be read without the service. Shipping restic, tusd, age, and Iroh as a separate field dropbox would hide a second product behind the same window. It would not make backup more primary. The plan change is the order: backup first after the MVP, preservation format unchanged and unseen.
