# Architecture Decision Record - FileSquid

039-cargo-hakari-workspace-hack.md

## Title

One feature set for shared Rust dependencies in test builds: a cargo-hakari workspace-hack crate used as a dev-dependency only

## Status

Accepted

Accepted (2026-10-18) — implementation subject to the measurement gate in Decision 7. If the gate fails, this ADR is marked Rejected, the crate and its gates are removed, and the index records why. Owner-requested decision. Changes no earlier ADR: module crates still build, test and publish alone ([ADR 029](./029-filesquid-unified-product-and-distributions.md) Decision 4), and Cargo features are still never the only boundary ([ADR 001](./001-shared-rust-core-with-tauri-and-axum-hosts.md)).

Amended 2026-10-19 (owner decision of 2026-10-18): the Context below records the toolchain as measured on 2026-10-18 (channel `stable`, then 1.97.0 in the containers). `apps/filesquid/rust-toolchain.toml` now pins the exact release 1.99.1 instead of the channel ([ADR 013](./013-cargo-svelte-workspaces.md) Versions amendment); the decision and its measurement gate are unchanged.

## Context / Requirement Reference

- Requirements: [T-052](../product-vision.md#api-and-hosts) (one Cargo workspace; each module crate builds and tests on its own), [C-047](../product-vision.md#module-rules) and [C-048](../product-vision.md#module-rules) (modules build, test and publish alone), AGENTS.md section 5 (every gate runs locally in `scripts/pre-commit.sh`) and section 17 (minimise and pin dependencies).
- **The hook builds the same third-party crates more than once.** Its full-scope Rust steps ([`scripts/verify_tests.sh`](../../scripts/verify_tests.sh)) run, in the `apps/filesquid` workspace: `cargo clippy --workspace --all-targets`, `cargo test --workspace`, `cargo test -p <crate>` for each of `filesquid-core`, `-ocfl`, `-metadata`, `-c2pa`, `-api` and `-native` alone (the ADR 029 check), `cargo doc --workspace --no-deps`, and Clippy and tests for `filesquid-desktop` with `--features test-webdriver`. A scoped run (`rust:<crates>`) runs the same steps with `-p` for the changed crates and their dependents. Cargo unifies features per invocation, over the packages that invocation selects. `cargo test -p filesquid-ocfl` therefore resolves `serde`, `serde_json`, `tokio`, `cucumber` and their dependencies with fewer features than `cargo test --workspace`. Each distinct feature set has a different artifact hash, so each one compiles again, even in a warm shared target.
- **The other build levers are already in place.** The cloud containers have 4 cores. Their stable toolchain is 1.97.0 (`rust-toolchain.toml` pins the channel `stable`), which links with LLD by default on `x86_64-unknown-linux-gnu`: the binaries' `.comment` section names `Linker: LLD 22.1.6`. [`scripts/lib/cargo_shared.sh`](../../scripts/lib/cargo_shared.sh) exports `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=0`, and agents share one locked `CARGO_TARGET_DIR` ([local verification](../../.agents/rules/local-verification.md#shared-cargo-target), [change-aware pre-commit walkthrough](../tasks/Task-build-change-aware-pre-commit-Walkthrough.md)). Test targets are declared as explicit `[[test]]` entries, and a crate has several test binaries (for example 16 in `filesquid-api`, 22 in `filesquid-c2pa`).
- **Cargo's own fix is not stable.** With `[resolver] feature-unification = "workspace"` in `.cargo/config.toml`, cargo 1.97.0 prints ``warning: ignoring `resolver.feature-unification` without `-Zfeature-unification` `` and builds as before (checked 2026-10-18).
- **Guards that any fix must keep green, unchanged.** The graph guards run `cargo tree` over normal and build edges only: [`filesquid-api`](../../apps/filesquid/crates/api/tests/support/isolation.rs) (no Tauri, SQLite, `filesquid-native`, network client or alternative runtime, for default, no-default and all features) and [`filesquid-c2pa`](../../apps/filesquid/crates/c2pa/tests/support/deps.rs) (no other `filesquid-` package, no Axum, Tauri, Hyper, Tokio or Mio). The manifest guards read the `[dependencies]` table: [`filesquid-core`](../../apps/filesquid/crates/core/tests/unit/isolation.rs) requires exactly `serde`, [`filesquid-metadata`](../../apps/filesquid/crates/metadata/tests/unit/isolation.rs) forbids hosts, codecs and `filesquid-core`. The `filesquid-ocfl` BDD step "it should build and publish without other FileSquid crates" fails if its whole `Cargo.toml` contains `path = "../`. The [`filesquid-server` feature guard](../../apps/filesquid/crates/server/tests/unit/native_features.rs) fails if the server's feature tree enables `filesquid-native`'s `desktop` feature. The rule behind them is [src-isolation.md](../../.agents/rules/src-isolation.md) (Rust exception handling): module crates never depend on Axum, Tokio-net, `tauri` or `filesquid-native`; `apps/filesquid/` stays extractable.
- **Why a normal workspace-hack dependency breaks those rules.** `filesquid-api` already resolves Tokio with `net`, `mio` and `socket2` (through Axum's default `tokio` feature). A workspace-hack crate that unifies over the whole workspace would carry those features, and any host-only crate built with two feature sets (such as a `tauri-*` crate), into the normal graph of every crate that depends on it: Tokio-net in `filesquid-ocfl` and `filesquid-metadata`, Tauri crates in `filesquid-api` and `filesquid-server`, and the host features in WASM builds and published crates.

## Decision

1. **A generated workspace-hack crate.** The workspace gains `apps/filesquid/crates/workspace-hack/`, package `filesquid-workspace-hack`, `publish = false`, created with `cargo hakari init` and filled by `cargo hakari generate`. Its `lib.rs` holds only the crate-level documentation comment the inline-documentation mandate requires. It declares no binary and no feature of its own.
2. **Pinned tool, configuration in the workspace.** cargo-hakari is pinned to 0.9.39 (the newest stable release on crates.io, published 2026-09-19; it requires Rust 1.91 or later). Contributors install it with `cargo install cargo-hakari --locked --version 0.9.39`, which is the same command on Linux, macOS and Windows. The configuration is `apps/filesquid/.config/hakari.toml`, inside the extractable workspace:
   - `hakari-package = "filesquid-workspace-hack"`, `resolver = "2"` (matching the workspace), and the newest `dep-format-version` that 0.9.39 offers.
   - `platforms = ["x86_64-unknown-linux-gnu", "aarch64-apple-darwin", "x86_64-apple-darwin", "x86_64-pc-windows-msvc"]`: the containers, the macOS MVP target ([ADR 035](./035-macos-first-desktop-mvp.md)) and the later desktop targets. `wasm32-unknown-unknown` is not listed; see Decision 4.
   - Every workspace member is traversed, so the hack carries the feature set that `cargo test --workspace` resolves. `traversal-excludes` and `final-excludes` stay empty unless the gate in Decision 7 requires otherwise.
   - `workspace-hack-line-style = "workspace-dotted"`, so a crate refers to the hack as `filesquid-workspace-hack.workspace = true` and never with `path = "../…"`. `apps/filesquid/Cargo.toml` declares `filesquid-workspace-hack = { path = "crates/workspace-hack" }` under `[workspace.dependencies]`, with no `version` key.
3. **Dev-dependency only.** Every workspace member except the hack lists `filesquid-workspace-hack.workspace = true` under `[dev-dependencies]` and nowhere else. The hack MUST NOT appear in a `[dependencies]` or `[build-dependencies]` table, top-level or under `[target.*]`, in any crate.
   - Effect: the commands the hook runs with dev-dependencies active (`cargo test`, `cargo clippy --all-targets`, workspace-wide or `-p`) resolve one feature set for every shared third-party crate and reuse each other's artifacts. Commands without dev-dependencies (`cargo build`, `cargo check --lib`, `cargo doc`, release, WASM and `cargo publish` builds) never see the hack and resolve exactly the graph they resolve today.
   - Because the hack is dev-only, `cargo hakari manage-deps` is not used. It treats a dev-only link as missing and would move it to `[dependencies]`; the lines are written by hand once and checked by the gate in Decision 5.
4. **Module crates, WASM and publishing are untouched.** A module crate's runtime graph, `cargo build --target wasm32-unknown-unknown` and its published manifest do not contain the hack, because none of them include dev-dependencies. Cargo leaves a dev-dependency that has a path and no version out of the published manifest. Every crate carries `publish = false` today, so this cannot be checked yet. The first change that makes a module crate publishable (removes `publish = false` from it, and from any FileSquid crate it depends on, which must be published first: `filesquid-ocfl` before `filesquid-metadata`) MUST confirm with `cargo publish --dry-run -p <crate> --locked` that the packaged manifest has no hack line. If Cargo keeps the line, that crate is published with `cargo hakari publish -p <crate>`, cargo-hakari's documented flow. If WASM test builds are added later, their crates move the line to `[target.'cfg(not(target_arch = "wasm32"))'.dev-dependencies]`, which the gate in Decision 5 accepts as a dev-dependency.
5. **Hook gate, so the hack never drifts.** A new `scripts/verify_hakari.sh`, called from `scripts/pre-commit.sh` and documented in the root README "Run tests" section ([local-verification.md](../../.agents/rules/local-verification.md)), fails when:
   - `cargo hakari generate --diff` exits non-zero (the hack is out of date with `Cargo.lock`);
   - any member lacks the dev-dependency line, or any manifest lists the hack outside `[dev-dependencies]` (this check replaces `cargo hakari manage-deps --dry-run`, which cannot express a dev-only link);
   - cargo-hakari is missing or is not 0.9.39 (the message names the install command).
   It runs in the `full` scope and in every `rust:` scope, through `cargo_locked`. A change to `apps/filesquid/Cargo.toml`, `Cargo.lock` or `.config/hakari.toml` already gives the `full` scope, but a change to a crate's own `Cargo.toml` (a feature added to an existing dependency, or the hack line moved) only gives `rust:<crate>`, so the gate MUST NOT be limited to the `full` scope. It is skipped only in the `docs` and npm-only scopes, where no Cargo manifest changed.
6. **Guards stay unchanged, and why they still pass.** The graph guards query normal and build edges, and the manifest guards read `[dependencies]`; a dev-only edge is invisible to both, so no guard learns about the hack and none is edited. The `filesquid-ocfl` `path = "../` step passes because of the workspace-dotted line. The server feature guard passes because workspace members are never part of the hack, so it cannot carry `filesquid-native`'s `desktop` feature. The `filesquid-c2pa` rule that rejects every other `filesquid-` package is kept as a tripwire: if the hack ever became a normal dependency of `filesquid-c2pa`, that guard fails. The implementing change MUST run every guard unchanged and record the result.
7. **Measurement gate.** On one machine, measure wall-clock time of the Rust steps of `FULL=1 bash scripts/pre-commit.sh`, and of a typical scoped run (`rust:filesquid-ocfl`), with and without the hack, each from a cold shared target (empty `CARGO_TARGET_DIR`) and from a warm one (second identical run), with no other build using that target. Keep the hack only if the full-scope Rust steps are at least 20% faster both cold and warm, the scoped run is not slower, and every guard test and the ADR 029 checks in Decision 8 pass. Before rejecting, the implementing change MAY try one narrower configuration (the hosts `filesquid-desktop`, `filesquid-server`, `filesquid-native` and `filesquid-cli` under `traversal-excludes`) and measure it the same way. The raw timings go in the implementing task's walkthrough.
8. **The ADR 029 standalone check, kept honestly.** With the hack, `cargo test -p <crate>` resolves the unified feature set, so it no longer proves that a crate does not rely on features another crate enables. The proof moves to commands that exclude dev-dependencies:
   - In the full scope, the hook adds `cargo check -p <crate> --lib --locked` for each crate it now tests alone (`filesquid-core`, `-ocfl`, `-metadata`, `-c2pa`, `-api`, `-native`). The library resolves only its own features, so a missing feature fails to compile. Scoped runs use the unified graph only.
   - Before a module crate is published, its full test suite runs alone in a temporary copy of `apps/filesquid` with the dev-dependency lines removed (or the hack emptied with `cargo hakari disable`), and `cargo publish --dry-run` builds the packaged crate on its own.
   - What is given up: on ordinary commits the tests no longer run against a crate's minimal feature set. A difference that only shows at run time, such as JSON key order changing because another crate enabled `serde_json`'s `preserve_order`, is caught only by the pre-publication run. Today the `cargo test --workspace` step already runs every crate's tests with the unified features of the whole workspace.

## Rationale

- Rebuilding shared dependencies for every distinct feature set is the remaining avoidable cost in the hook: compilation is CPU-bound on 4 cores, and LLD, no incremental compilation, no debuginfo and a shared target are already in place.
- cargo-hakari is the established tool for this on stable Cargo. Its output is generated and checked, not hand-maintained, and it unifies per platform.
- Dev-only placement keeps every boundary the project depends on outside the hack's reach. Runtime graphs, release binaries, WASM builds and published manifests do not change, so the src-isolation rules, the privacy rule that features are never the only boundary (ADR 001) and the guard tests hold without edits. The hook gets most of the benefit, because its expensive steps are test and Clippy runs.
- The measurement gate makes the decision reversible on evidence. Hakari makes a scoped run compile the whole hack, so module-only cold builds can get slower; the owner accepts the crate only if the numbers favour it.

## Assumptions

- The repeated compilation of shared dependencies under different feature sets is a large enough share of the hook's Rust time for a 20% gain to be possible; the gate tests this assumption.
- cargo-hakari 0.9.39 computes the hack from each member's default, no-default and all-feature builds, with and without dev-dependencies (as its `hakari` 0.18.0 library does), and generates correctly for this workspace on the containers' toolchain.
- `cargo tree` resolves features without dev-dependencies when dev edges are not requested, so the graph guards keep seeing today's graph. Checked on 2026-10-18: `cargo tree -p filesquid-api -e normal,build,features` shows no Tokio `rt-multi-thread` feature, which only `filesquid-api`'s dev-dependency enables; adding `dev` to `-e` shows it.
- Contributors and agents can install one more pinned Cargo tool; the setup script can install it.

## Alternatives Considered

- **Status quo.** Keeps the repeated rebuilds that motivated the owner's request. Remains the fallback if the gate fails.
- **Cargo's `resolver.feature-unification = "workspace"`.** Does the same without an extra crate, but is unstable: cargo 1.97.0 ignores it without `-Zfeature-unification`. Revisit when it is stabilised; it is the likely end state and would supersede this ADR and remove the crate.
- **A hakari-managed normal dependency (hakari's default).** Unifies `cargo build` too, but puts Tokio-net, Tauri crates and host features into module, server, WASM and published graphs, breaking src-isolation and the guards. Rejected.
- **Align features by hand in `[workspace.dependencies]`.** No tool, but transitive dependencies cannot be aligned this way, and nothing detects drift. Rejected.
- **sccache.** Little gain: containers are ephemeral, the target directory is already shared, and a different feature set misses the cache anyway. Rejected.
- **Drop the per-crate-alone step.** The fastest option, but it removes the ADR 029 check. Rejected; Decision 8 keeps a cheaper form.
- **Fewer test binaries per crate.** A separate lever that reduces link time, not dependency rebuilds. Not decided here.

## Consequences / Implications

- Easier: test and Clippy runs, workspace-wide or per crate, reuse one set of dependency artifacts in the shared target; the per-crate steps of the full scope and most scoped runs stop recompiling `serde`, `tokio`, `cucumber` and friends.
- Harder: one more generated crate and one more hook gate. Every dependency change also needs `cargo hakari generate`, committed with the `Cargo.lock` change, or the gate fails.
- Harder: every contributor needs cargo-hakari 0.9.39 installed. The README setup section and `scripts/setup-dev-environment.sh` gain the install command when this is implemented.
- Harder: a scoped test of one module crate compiles the whole hack, including crates only the hosts use. In a warm shared target they are already built; from a cold one this can be slower, which the gate measures.
- Harder: the ADR 029 check on ordinary commits becomes a compile check of each library alone; full stand-alone test runs happen before publication (Decision 8).
- Non-test builds (`cargo build`, `cargo doc`, release and WASM builds) are not sped up and not changed.
- The implementing task records its timing data and guard results in its walkthrough; if the gate fails, this ADR is marked Rejected and the crate, configuration and gate are removed.
