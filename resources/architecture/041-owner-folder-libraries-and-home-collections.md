# Architecture Decision Record - FileSquid

041-owner-folder-libraries-and-home-collections.md

## Title

One library model: every library lives in an owner-chosen folder, and every file has exactly one home collection

## Status

Accepted

The work is planned inside the FileSquid MVP, before gate Task FS-3.9 ([implementation plan](../implementation-plan.md)).

## Context / Requirement Reference

- Requirements: [PRD F-001](../prd.md#f-001-independent-local-library-and-ownership) (local library, rebuild without the operational database), [PRD F-002](../prd.md#f-002-safe-file-folder-and-device-import) (import review shows the destination), [PRD F-004](../prd.md#f-004-collections-folders-and-navigation) ("A file's bytes MUST live in exactly one collection"), [PRD F-009](../prd.md#f-009-multiple-libraries-and-filesystem-administration) (multiple libraries, relocation), [PRD F-042](../prd.md#f-042-ocfl-preservation-and-portable-recovery) (OCFL as the source of truth), vision [FE-065](../product-vision.md#independent-library) and [U-03](../product-vision.md#platform-ownership-and-access).
- Until this decision, `main` had two library models side by side:
  - **Catalog libraries** (Task DE-0.2, [DE-S-009](../../apps/filesquid/crates/desktop/resources/srs.md), [DE-S-010](../../apps/filesquid/crates/desktop/resources/srs.md)): a SQLite catalog `libraries/<library-id>.sqlite` and an OCFL storage root `libraries/<library-id>.ocfl/` both inside the app's data directory. They hold collections, folders and virtual collections, but the file service did not serve their OCFL roots.
  - **Folder libraries** (Task DE-1.1, [DE-S-018](../../apps/filesquid/crates/desktop/resources/srs.md)): libraries in folders the owner chose through the native folder dialog, registered under opaque location IDs and served by the file service. Their `CatalogFolders` and `CatalogScopes` list no folders or objects yet.
- Uploads (Task API-F1.4) and desktop imports (Task DE-1.2, [API-S-036](../../apps/filesquid/crates/api/resources/srs.md)) commit file objects into folder libraries but register no home collection. Uploaded and imported files are therefore invisible in navigation, and the browser's drop-target label "Drop to upload into {folder}" (`fileDropTarget` in the default UI's label table) promises a placement the API does not make. A request naming a `collection_id` is refused as `collection_not_supported`.
- Task DE-1.7 (desktop plan) planned indexing imports into catalog libraries only, and recorded that the owner would be asked about the two models before it starts.

## Decision

1. **Folders only.** Every library MUST live in a folder the owner chooses (through the location-choices route of [API-S-034](../../apps/filesquid/crates/api/resources/srs.md) on the desktop). The library folder MUST hold only the library's OCFL storage root: the collection-snapshot object, one object per file, and the library's own journal and history OCFL objects ([API-S-032](../../apps/filesquid/crates/api/resources/srs.md), [ADR 033](./033-activity-journal-and-live-health-monitoring.md), [ADR 040](./040-prov-o-history.md)), as the FileSquid OCFL application profile defines ([API-S-026](../../apps/filesquid/crates/api/resources/srs.md)). A host that cannot let the owner choose a folder (no `LocationChooser`, such as `filesquid-server` until it has a location registry) MUST answer the location-choices route `503 unavailable` (API-S-034) and MUST NOT create or open a library anywhere else. A host MUST NOT create a library's OCFL storage root, originals or metadata records in its data directory. In-app catalog libraries (`libraries/<library-id>.ocfl/` in the data directory) are retired; no library with real data exists in that form, so no migration is provided.
2. **Catalog index in the app data directory.** Each library's catalog index MUST be the SQLite file `libraries/<library-id>.sqlite` in the host's data directory, keyed by the library's UUID v4, as DE-S-009 specifies. It holds no file bytes. It MUST be rebuildable from the library folder alone. Writer staging and version leases MAY stay in the data directory beside it (`libraries/<library-id>.work/`), outside the storage root, as DE-S-018 already requires for owner-chosen folders.
3. **One library model.** Every library has collections, folders and virtual collections ([PRD F-004](../prd.md#f-004-collections-folders-and-navigation)). Every file MUST have exactly one **home collection**, and deletion is a state, not a place (Decision 8): a recoverably deleted file keeps its OCFL object, its logical path and the identifier of its home collection, even when that collection has since been deleted. No file is ever "unfiled". A folder is a prefix of the logical paths of files inside one collection.
4. **Every write names a destination.** An upload, an import and a copy MUST name a destination collection (and MAY name a folder inside it). A move MUST name its destination collection or folder. A request without a destination MUST be refused before anything is staged or any dialog is shown. There is no upload or import at a library's top level and no default collection; the owner's one exception is restore (Decision 9), which creates an "untitled collection" when a restored file's home collection is gone. Each of these operations MUST register the file in its home collection at its logical path, under the operation's ID, in the collection snapshot, and MUST be journaled like every other domain operation ([ADR 033](./033-activity-journal-and-live-health-monitoring.md)). A file uploaded into a folder therefore appears in that folder at once, and "Drop to upload into {folder}" stays accurate.
5. **The snapshot is the source of truth.** The collection snapshot inside the library folder MUST record, for each file, its home collection, its logical path inside that collection, the identifier of its file object and, while it is recoverably deleted, its `deleted_at` and `purge_after`, and for the library its own retention period when the owner set one (Decision 10), so the catalog index can be rebuilt from the snapshot alone (amends [ADR 010](./010-ocfl-1-1-dual-profile.md)). The per-library SQLite catalog is a rebuildable index (amends [ADR 005](./005-sqlite-local-postgres-hosted.md)).
6. **Moved and copied libraries rebuild.** Opening a library folder whose catalog index is missing, belongs to another copy, or does not match the snapshot head MUST rebuild the index from the folder, in one journaled reconcile ([DE-S-010](../../apps/filesquid/crates/desktop/resources/srs.md)). A copy keeps its library UUID, so while one folder of a library is open, opening another folder with the same library UUID MUST be refused (`library_already_open`, as the library routes already answer), and two folders never share one index at once. A file object that the snapshot does not register (committed by an earlier build without a home collection) MUST be reported by the rebuild and MUST NOT be placed in an invented collection.
7. **The default UI follows the rule.** Upload and import controls MUST target a folder or collection; the drop target MUST appear only over one; the import dialog MUST require a destination before it starts ([UI-S-002](../../apps/filesquid/ui/resources/srs.md)).
8. **Recently deleted is a filter over the deleted state (owner decisions 2026-10-22).** The owner first wrote: "RE: deletion question in #124, when users delete a collection that still holds files, those files go into a "Recently deleted" top-level directory within their library. That directory has a default 30 day retention period before files inside are expunged for good." The owner then replaced the "top-level directory" with a filter: ""Recently deleted" aka Trash can will be a navigation filter over collection items with the deleted state. They are not moved. They are completely deleted from library and filesystem after recently deleted retention period expires."
   - **Deletion is a state.** Deleting a collection that still holds files MUST remove the collection and mark each of its files that is not already deleted as recoverably deleted, in the same command and version. Nothing is moved: each file keeps its OCFL object, its logical path and the identifier of its home collection. A file that was already deleted keeps its earlier `deleted_at` and `purge_after`. This reuses the recoverable deletion that already exists ([PRD F-008](../prd.md#f-008-deletion-hidden-files-and-duplicate-review), [API-S-019](../../apps/filesquid/crates/api/resources/srs.md)): there is no second trash and no physical folder in the storage root.
   - **Recently deleted (Trash)** is a reserved navigation filter of each library over its files in the deleted state, never a collection, a folder or a storage location: it cannot be created, renamed, deleted or chosen as an upload, import, copy or move destination. It MUST list every deleted file of the library, whether it was deleted one by one or with its collection: the owner decided "3. yes, single-file deletes use the same Trash", so a single-file delete puts the file in the same deleted state, under the same retention (Decision 10), expiry (Decision 11) and restore (Decision 9) rules. There is one Trash and one retention rule. The navigation listing shows it as a reserved node of each library ([API-S-021](../../apps/filesquid/crates/api/resources/srs.md)). Search finds these files with `is:deleted`; `is:unfiled` and the "unfiled" quick filter are retired.
   - **Expiry.** When a file's retention period ends, the host MUST expire it as Decision 11 says, as a recorded `purge` operation, journaled ([ADR 033](./033-activity-journal-and-live-health-monitoring.md)) and with its PROV-O activity ([ADR 040](./040-prov-o-history.md)), never a silent delete.
9. **Restore (owner decision 2026-10-22, the one exception to "no default collection").** The owner's words: "Into its original OCFL object and relative filepath inside FileSquid. If its original collection is gone create a new one "untitled collection" and put the restored file inside. If the name "untitled collection" is already taken then just add numberical increments as name suffix, eg "untitled collection 2, untitled collection 3, etc)"
   - A restored file MUST return to its original OCFL object and its logical path, in its home collection when that collection still exists. If that path is taken all the same, Decision 12 applies.
   - When its home collection no longer exists, the host MUST create a collection titled "untitled collection" in the file's library and place the file there at its logical path. When a collection of that library already has that title, the host MUST use "untitled collection 2", "untitled collection 3" and so on, the first free number. One restore command creates at most one such collection for each home collection that is gone, and places every file of the command that came from that collection in it (orchestrator's reading, owner to confirm).
   - The name search MUST be bounded at 9,999: titles "untitled collection" to "untitled collection 9999" (owner decision: "Caps: 9999 for both"). When all are taken, the restore MUST be refused as `409 conflict` with the code `restore_name_exhausted`, change nothing, and be journaled as `failed` with that code.
   - Creating the collection and restoring the file MUST be one journaled operation, committed as one snapshot version under one operation ID, with its PROV-O activity.
   - This is the owner's one exception to Decision 4's "no default collection"; it applies only to restore.
10. **Retention scope (owner decision 2026-10-22).** The owner's words: "The 30 days defaut retention policy for any files moved to the "Recently deleted" trashcan applies across the whole installation and be configured per library"
    - The installation-wide default retention MUST be 30 days. The admin MAY change it; on the desktop the admin is the owner. It MUST be stored in the host's operational store (on the desktop `<data dir>/filesquid.sqlite`, [DE-S-014](../../apps/filesquid/crates/desktop/resources/srs.md)), because it belongs to the installation and not to any one library.
    - Each library MAY set its own retention period, which overrides the installation default for that library. It MUST be stored with the library, in its collection snapshot (Decision 5), so it moves with the library folder and survives an index rebuild; the catalog index MAY cache it. These storage places are the orchestrator's choice under Decisions 1, 2 and 5, owner to confirm.
    - A retention period MUST be a whole number of days from 1 to 3,650 (proposed bounds, owner to confirm). Changing either setting MUST be a journaled command and MUST NOT change the `purge_after` of a file already deleted, which keeps the expiry shown at its deletion ([PRD F-008](../prd.md#f-008-deletion-hidden-files-and-duplicate-review)).
11. **Expiry setting (owner decisions 2026-10-22).** The owner's words: "Okay, keep the version history by default but provide an admin config option to delete the version history as well", and then: "Okay, if the "delete all version history" setting is enabled then the OCFL and any index entries are deleted when the retention period expires, along with the files and metadata, etc.. If the "keep version history" setting is enabled then keep those source OCFL objects in the library, with only version history, no other content."
    - Retention expiry MUST be governed by one setting with two values, **keep version history** (the default) and **delete all version history**. The admin MAY switch it; on the desktop the admin is the owner. It is an installation setting in the host's operational store, like the default retention of Decision 10 (orchestrator's reading of "admin config option", owner to confirm).
    - **Delete all version history:** at expiry the host MUST delete the file's OCFL object, its index entries, the file and its metadata.
    - **Keep version history, the tombstone (owner decisions 2026-10-22: "yes, for deletion with version history kept, use the tombstone model where the OCFL object remains in the library but ALL of its contents other than version history is fully deleted"; then "fine on your proposed method to keep tombstone a valid OCFL but then make sure that the original deletion and tombstone creation are also an event in the version history"):** at expiry the OCFL object MUST remain in the library under the same object identifier and at the same path, but ALL of its content other than the version history MUST be fully deleted: the file's bytes, its metadata record and any derivatives. OCFL 1.1 cannot remove content from past versions of an existing object, so, to stay valid OCFL 1.1, the host MUST delete the original object and recreate it as a **tombstone** with the same identifier at the same path (the orchestrator's method, approved by the owner).
      - The tombstone MUST hold only history: the facts of every former version (number, `created`, `user`, `message`, and the digests and sizes of its content, without bytes), the PROV-O records, and a purge record naming the expiry.
      - Its version history MUST record both events as events of their own: the deletion of the original object (operation kind `purge`) and the creation of the tombstone. The tombstone's own first version is the tombstone creation; its history carries the original object's deletion event after the facts of every former version. Each event has its time, its actor (the installation, or the admin when the expiry is started by hand), its operation kind and its PROV-O activity ([ADR 040](./040-prov-o-history.md)), linked to its journal entry. [CO-0.11](../../apps/filesquid/crates/core/resources/plan.md)'s operation kinds have no kind for the tombstone's creation, so the implementing task adds `tombstone` to them; no PROV-O vocabulary beyond ADR 040 is added.
      - A crash part-way MUST NOT leave a half-deleted object: OCFL recovery and repair (validation warning codes, W-codes; [OCFL-S-018](../../apps/filesquid/crates/ocfl/resources/srs.md), [OCFL-S-020](../../apps/filesquid/crates/ocfl/resources/srs.md), [OCFL-S-022](../../apps/filesquid/crates/ocfl/resources/srs.md)) MUST complete or report an interrupted tombstone write; the mechanism is the implementing task's.
      - The file's index entries MUST be removed or marked purged, so it never reappears in navigation, and a library recovered from OCFL alone MUST show a tombstone as purged history, never as a file.
    - Every expiry MUST be a recorded `purge` operation under one operation ID, journaled and with its PROV-O activity in the library's journal and history objects (Decision 1), which the purge does not delete. The purge MUST be recorded in the journal before or with the deletion, so a crash never leaves a deletion without its record.
    - This is the owner's exception to [PRD F-065](../prd.md#f-065-file-version-history-and-retention)'s promise that FileSquid never deletes versions or their content; the promise stands for every other case.
12. **Duplicate logical paths (owner decision 2026-10-22).** The owner's words: "Filesquid should simply add an incremental number to the new file path so its sits next to conflicting filepath. Eg if filepathX/directoryY already exists and the user wants to create a new directory for a new import at the pre-existing filepathX/directoryY then FileSquid would name the new directory filepathX/directoryY-1, and then filepathX/directoryY-2 and so on."
    - When an upload, import, copy, move, rename or folder creation would give a new item a logical path that already exists in its collection, FileSquid MUST add an increasing number so the new item sits beside the first. It MUST NOT refuse the request or overwrite the existing item.
    - Folders: `directoryY` becomes `directoryY-1`, then `directoryY-2`: a hyphen and the first free number, starting at 1, at the end of the folder name.
    - Files (owner decisions 2026-10-22: "no, put the number of the first part of the filename, before the first dot", replacing "yes, number goes before the exentsion"; and "yes, the edge is correct especially because the leading dot has operational implications"): the number goes after the first part of the file name, before the first dot: `photo.jpg` becomes `photo-1.jpg`, then `photo-2.jpg`, and `archive.tar.gz` becomes `archive-1.tar.gz`. A name without a dot takes the number at its end. A name that starts with a dot keeps that dot as part of its first part, so `.env` becomes `.env-1` and `.config.json` becomes `.config-1.json`: a numbered copy stays a dotfile and keeps the hidden-file behaviour that tools and operating systems give a leading dot, which is the owner's reason ("the leading dot has operational implications").
    - A path held by a recoverably deleted file counts as taken, because a deleted file keeps its place (Decision 8) and its restore returns it there (Decision 9) (orchestrator's reading, owner to confirm).
    - The search MUST be bounded at 9,999 numbers, `-1` to `-9999` (owner decision: "Caps: 9999 for both"). When all are taken, the request MUST be refused as `409 conflict` with the code `path_suffix_exhausted`, change nothing, and be journaled as `failed` with that code.
    - Stored names `<file-uuid>.<ext>` never collide; this rule is about logical paths and display names only.

## Rationale

- One model removes the gap between the two library kinds: collections, folders and virtual collections work in the libraries the owner actually uses, and the file service serves exactly those libraries.
- Keeping only OCFL in the library folder keeps it clean for ordinary tools and portable: the owner can move, copy or inspect it, and FileSquid rebuilds its index ([FE-065](../product-vision.md#independent-library)). A SQLite file inside the folder would be a second, live format beside OCFL, and copying a live SQLite file is not a supported backup ([ADR 005](./005-sqlite-local-postgres-hosted.md)).
- Refusing a request without a destination keeps PRD F-004's rule that a file's bytes live in exactly one collection, without inventing a default collection that the owner never chose.
- Recording the home collection and logical path in the snapshot keeps the index rebuildable, which the commit sequence of ADR 005 already requires.
- Deletion as a state, with Recently deleted as a filter (Decision 8), keeps every file in its OCFL object and at its logical path, so a restore is a state change and needs no second copy or move of bytes, and a library folder copied with ordinary tools still shows its deleted files where they were.
- Numbering a new item beside an existing one (Decision 12) never loses or overwrites data, and a bounded search keeps every write route finite (AGENTS.md §22).

## Assumptions

- No library with real data exists in the data directory form (owner statement, 2026-10-22), so retiring it needs no migration.
- The navigation listing ([API-S-021](../../apps/filesquid/crates/api/resources/srs.md)) and the file routes can address a collection and a folder inside it with opaque handles and identifiers, without exposing a filesystem path.
- A library folder can be large; a rebuild of its index stays bounded by the existing snapshot limit (1,000,000 entities, [DE-S-010](../../apps/filesquid/crates/desktop/resources/srs.md)) and runs as a journaled reconcile at open.

## Alternatives Considered

- **Keep both models (catalog libraries and folder libraries):** two code paths for the same product concept, and uploads and imports would still need a rule for which model they land in. Rejected by the owner ("Folders only").
- **Migrate in-app catalog libraries into owner folders:** cost with no benefit, since none holds real data. Rejected by the owner.
- **A default collection for uploads and imports with no destination** (for example "Unsorted"): places files where the owner did not choose and hides them behind a name the owner never created. Rejected by the owner ("Must choose").
- **For a collection that still holds files when it is deleted:** (a) refuse the deletion until its files are moved; (b) ask for a destination collection and move the files there; (c) keep "unfiled" as a recoverable state only collection deletion can produce. None was chosen: the owner chose recoverable deletion with a Recently deleted filter (Decision 8).
- **A physical Recently deleted folder in the library's storage root**, where deleted files are moved: the owner's first wording ("a "Recently deleted" top-level directory"). Replaced by the owner ("They are not moved"): a move would rewrite logical paths and lose the place a restore returns to.
- **On restore, ask the owner for a destination when the home collection is gone:** consistent with "Must choose", but rejected by the owner, who chose an "untitled collection" (Decision 9).
- **Refuse or overwrite a new item at a logical path that already exists:** rejected by the owner, who chose numbering beside the first (Decision 12).
- **Under "keep version history", keep the whole original object, bytes included, hidden from the library** (option B of question 4b): keeps content the owner wanted deleted. Rejected by the owner, who chose the tombstone (Decision 11).
- **Always delete the whole object at expiry:** breaks PRD F-065's history promise without the owner's choice. The owner chose a setting whose default keeps the version history (Decision 11).
- **Upload into the library's top level:** a file outside every collection breaks PRD F-004's "exactly one collection". Rejected by the owner.
- **Catalog index inside the library folder:** keeps the index with the library when it moves, but puts a live SQLite file next to OCFL, where ordinary tools copy it unsafely. Rejected by the owner ("App data directory").

## Consequences / Implications

- Easier: one library model in the API, the desktop host and the UI; uploaded and imported files appear in navigation at once; the folder can be copied or moved with ordinary tools and reopened.
- Harder: the snapshot's file entity gains the logical path and the file object identifier, so the catalog schema moves to version 3 and the snapshot reader accepts both forms; the import route requires `collection_id` and refuses requests without one (replacing `collection_not_supported`); the upload, copy and move routes gain destination parameters under a minor contract bump; uploads, imports and copies commit a file object and then a snapshot version under one operation ID, so a crash between them must leave the operation pending and resumable ([ADR 005](./005-sqlite-local-postgres-hosted.md) commit sequence).
- Harder (Decisions 8 to 12): restore can create a collection, so it commits that collection and the file's state in one snapshot version; two retention settings and one expiry setting are stored in two places (the operational store and the snapshot) and need their own journaled commands and contract fields; every write route needs a bounded numbering search over its collection's logical paths, deleted files included; the expiry job has two behaviours, and "keep version history" rewrites an object as a tombstone, which needs a new operation kind and crash recovery.
- Planned work (MVP, phases F0 to F3): desktop Task DE-1.7 widened to folder libraries and the retirement of the in-app catalog roots, with deletion as a state in the snapshot and duplicate-path numbering for imports (global Task 1.2); API Task API-F2.14 for uploads, copies, moves, renames and folder creation, with their destination and duplicate-path numbering (global Task FS-2.5); UI Task UI-F2.17 for the default UI (global Task FS-2.5); API Task API-F2.15 for the Recently deleted filter, restore, the retention and expiry settings, the expiry job and the retirement of "unfiled" (global Task FS-2.5, Decisions 8 to 11).
- Closed by Decision 8: the Conflict Artifact of the [walkthrough](../tasks/Task-docs-library-model-owner-folders-Walkthrough.md) about "unfiled" files (a deleted collection's files, the `is:unfiled` operator and quick filter, the navigation listing's unfiled folders). The code that implements "unfiled" today (catalog, navigation and search) is retired by API Task API-F2.15 and desktop Task DE-1.7.
