## Context / Requirement Reference

FileSquid has one Rust backend and several plain HTML, CSS and TypeScript UIs ([ADR 029](./029-filesquid-unified-product-and-distributions.md), [ADR 031](./031-vanilla-typescript-ui-and-white-label-theming.md)). The UIs MUST reach every feature through one versioned API ([FE-074](../product-vision.md#platform-api-and-hosts), [U-16](../product-vision.md#one-api-hosts-and-distributions)). That API MUST be served by the desktop host and by `filesquid-server` ([FE-075](../product-vision.md#platform-api-and-hosts)), and later by an encrypted browser host ([ADR 032](./032-hosting-and-privacy-model.md)).

Constraints:

- The contract MUST be versioned, owned by `filesquid-api`, published in the repository, with generated TypeScript types and a drift test ([T-048](../product-vision.md#api-and-hosts)).
- The desktop host MUST serve the API in-process without a TCP port, unless an ADR records otherwise ([T-049](../product-vision.md#api-and-hosts), [U-18](../product-vision.md#one-api-hosts-and-distributions), [FE-064](../product-vision.md#desktop-host-isolation), [ADR 002](./002-tauri2-desktop-shell.md)).
- The API MUST provide an event channel. HTTP and WebSocket MUST be evaluated against previews and ranged reads, uploads, push, the no-TCP-port rule, and Service Worker interception for the browser host ([T-050](../product-vision.md#api-and-hosts), [U-17](../product-vision.md#one-api-hosts-and-distributions)).
- `filesquid-server` is multi-user: it MUST authenticate users and enforce group and collection permissions on every call ([T-053](../product-vision.md#api-and-hosts), [U-06](../product-vision.md#platform-ownership-and-access)).

Before this record, the desktop UI called Rust through Tauri IPC commands (`health_ping`), the Axum service exposed its own `/health` route, and ADR 028 planned a separate view API and client adapter per engine.

## Decision

**1. One API, owned by `filesquid-api`.** The crate `filesquid-api` (`apps/filesquid/crates/api/`) owns every route, request and response type, error, auth check and event type. Hosts mount it; they add no routes of their own except static UI files on `filesquid-server`. Paths are versioned under `/api/v1/`. The first route is `GET /api/v1/health`, which replaces the desktop `health_ping` command and the server's `/health` route. Modules expose Rust APIs only; they never define HTTP routes.

**2. Contract.** The API contract is an **OpenAPI 3.1** document checked into `apps/filesquid/crates/api/`. TypeScript types for `@filesquid/ui` MUST be generated from it. A test MUST fail when the Rust routes, the OpenAPI document and the generated types drift. This is ADR 001's "versioned operation schemas, generated bindings" rule applied to the new boundary.

Generators (owner decision, 2026-10-17):

- **TypeScript:** the types in `apps/filesquid/ui/src/api/schema.d.ts` are generated with the npm package `openapi-typescript`, at the version pinned in `apps/filesquid/ui/package.json` (`npm run contract:types`).
- **Rust:** no generator. The contract is hand-written (contract-first). Drift tests in `filesquid-api` (`unit_contract`) check it against the router's route table in both directions, against serialized Rust payload types with a strict schema checker, and against the core constants (for example the page-size bound of [CORE-S-005](../../apps/filesquid/crates/core/resources/srs.md)).
- **Where the drift tests run:** in the local pre-commit hook (`scripts/pre-commit.sh`); the repository has no hosted CI. The Rust test is `unit_contract`; the TypeScript test is the Vitest `tests/unit/contract.test.ts` in `apps/filesquid/ui`.

**3. Transport-agnostic router.** `filesquid-api` exposes its routes as one `tower::Service` over `http::Request`/`http::Response`. It MUST NOT bind sockets or depend on Tauri. Each host adapts that one service:

| Host | How the UI reaches the API | Base URL |
|---|---|---|
| `filesquid-desktop` (Tauri 2) | A custom URI scheme registered with `tauri::Builder::register_asynchronous_uri_scheme_protocol`. The handler passes each webview request to the router in-process. No TCP port is opened. | `filesquid://localhost/api/v1/...` on macOS, iOS and Linux; `http://filesquid.localhost/api/v1/...` on Windows and Android |
| `filesquid-server` (Axum) | The router is mounted on an Axum `Router` and served over HTTP on a TCP port, next to the selected distribution's static UI files ([ADR 032](./032-hosting-and-privacy-model.md)) | Same origin as the UI (`/api/v1/...`) |
| Encrypted browser host (roadmap) | The router compiled to WebAssembly, reached through a Service Worker or a worker plus a client shim ([ADR 032](./032-hosting-and-privacy-model.md)) | Same origin |

**4. Transport evaluation and working recommendation.** These criteria come from existing requirements:

| Criterion | HTTP resources | WebSocket only | HTTP + WebSocket events |
|---|---|---|---|
| `<img>` and `<video src>` previews, `Range` reads, browser caching ([U-11](../product-vision.md#platform-ownership-and-access)) | Native | Needs blob URLs; no `Range`, no HTTP cache | Native |
| Streaming uploads of large originals | Native (chunked or multipart) | Binary frames; custom resume | Native |
| Push: job progress, change notifications, multi-window refresh | Polling or server-sent events | Native | Native |
| Desktop with no TCP port ([ADR 002](./002-tauri2-desktop-shell.md)) | Custom URI scheme works | Not possible without a loopback port | Requests through the custom scheme; events through a Tauri channel, behind one client interface |
| Future encrypted browser host through a Service Worker | `fetch` is interceptable | Service Workers cannot intercept the WebSocket handshake | Requests interceptable; events need an in-page shim |
| Server deployment behind proxies | Standard | Needs upgrade-aware proxy configuration | Both |

Working recommendation, to be confirmed or overturned by S1:

- **Requests and bytes** use the HTTP resource API on every host.
- **Push** uses **one event channel**: a WebSocket at `GET /api/v1/events` on `filesquid-server` (Axum `ws` feature), and a `tauri::ipc::Channel` on the desktop. Superseded for the desktop by S1 (b), which adopted Tauri events named `filesquid-event` (see **S1 results** and the desktop binding recorded below); `tauri::ipc::Channel` remains only the fallback if event throughput becomes a problem.
- The TypeScript client `FileSquidClient` in `@filesquid/ui` hides which transport answered. Its interface is `request()`, `read()`, `upload()` and `subscribe()`. Views MUST NOT call `fetch`, `WebSocket` or Tauri APIs directly.

Recorded 2026-10-17 (Task API-F1.2): event channel semantics. These implement the decision above inside `filesquid-api` (`events` module) and change no transport.

- **Topics.** The channel carries a closed set of topics, the contract's `EventTopic` enum: `process.update` (`ProcessView`), `journal.entry` (`JournalEntry`), `health.change` (`HealthReport`) and `events.resync` (`EventResync`). The OpenAPI extension `x-filesquid-event-payloads` on `GET /api/v1/events` names each topic's payload schema. Drift tests check the enum against the Rust topic constants and the events the crate's publishers emit against those schemas. Job progress travels as `process.update`, because every job registers in the process registry ([ADR 033](./033-activity-journal-and-live-health-monitoring.md)); change notifications for file operations are added with their routes (API-F1.3, API-F1.6).
- **Events are hints.** A client MUST NOT depend on receiving every event. A subscription never drops events silently: a subscriber that fell behind receives one `events.resync` event with the number it missed, and MUST reread the state it shows through the request routes. A client that reconnects MUST reread too.
- **Limits.** Each subscriber lags at most 256 events (`EVENT_BUFFER`); further lag becomes one `events.resync` hint followed by the newest 256 events. An event whose JSON encoding exceeds 65,536 bytes (`MAX_EVENT_BYTES`) is replaced by `events.resync` with `missed` 1 and counted. At most 64 client subscriptions are open at once (`MAX_SUBSCRIBERS`); the next one is refused with a retryable `unavailable` `ApiError`, and dropping a subscription frees its slot. Publishing never blocks, so a slow or vanished client cannot stall publishers or grow memory.
- **Host binding.** A host opens one `EventBus::subscription()` per client (each WebSocket session on `filesquid-server`, the desktop forwarder) and forwards every event it yields, `events.resync` included. When `subscription()` is refused, `filesquid-server` answers the upgrade request with that `ApiError` (HTTP 503) instead of upgrading. Until its host binding task ([SV-F1.1](../../apps/filesquid/crates/server/resources/plan.md)) moves it to `subscription()`, `filesquid-server` still forwards from the uncounted `EventBus::subscribe()` receiver and logs lag without forwarding the hint.

Recorded 2026-10-18 (Task DE-F1.1): the desktop binding. These implement the decision above in `filesquid-desktop` (`event_channel` module); S1 (b)'s Tauri events stay the transport.

- **One counted subscription.** The desktop opens one `EventBus::subscription()` for its webviews and emits every event it yields, `events.resync` included, as the Tauri event `filesquid-event`, which `FileSquidClient.subscribe()` listens to. If the bus refuses the subscription, the refusal is journaled (`desktop.events.subscription`, `unavailable`) and the API keeps working without push. The forwarder registers in the process registry as `event-forwarder` (heartbeat every 5 s, stall timeout 30,000 ms) and ends when the bus closes or the app exits.
- **Only the app's own webviews.** Tauri delivers an event to every webview that listens for it, so the host keeps every webview on the app's origins (the same list as the token script, plus `about:blank` and `about:srcdoc`): any other navigation is refused and journaled as `desktop.navigation.refused` with error code `foreign_origin`, never with the address. The default capability already limits event listening to the main window's app pages.

S1 MUST measure: (a) `Range` reads of a 100 MB file into `<img>` and `<video>` through the Tauri custom scheme on each desktop webview; (b) event push through a Tauri channel versus a loopback WebSocket guarded by a token; (c) WebSocket and HTTP on `filesquid-server`; (d) whether `EventSource` or streamed `fetch` answered by a Service Worker can carry events for the browser host. S1 MUST also measure a **loopback-port alternative** for the desktop (the same HTTP and WebSocket everywhere, guarded by a per-launch token). If that alternative wins, this ADR MUST say explicitly that it overturns ADR 002's no-local-server rule and T-049.

**5. Authentication and authorisation.** Every call is authorised by `filesquid-api` before it touches files, SQL or keys, deny-by-default ([U-18](../product-vision.md#one-api-hosts-and-distributions)).

- **Desktop:** one local owner. The host generates a per-launch token and gives it only to its own webviews. Requests without it are refused. Tauri capabilities stay deny-by-default ([ADR 002](./002-tauri2-desktop-shell.md)).
- **`filesquid-server`:** multi-user from the start. Users authenticate. Users belong to groups. Libraries are owned by a user or a group, and access is granted per collection. Group membership MUST NOT grant ownership of another member's libraries, and billing administration MUST grant no access to private libraries ([U-06](../product-vision.md#platform-ownership-and-access)). The account store, session format and password or federated login choice are left to a later ADR.
- The UI receives opaque handles, never raw filesystem paths or SQL.

Recorded 2026-10-17 (Task API-F1.7): the authorisation layer. It implements the decision above inside `filesquid-api` (`auth` module) and changes no transport.

- **One layer, deny-by-default.** Every route in the router's route table declares one action (`health.read`, `contract.read`, `events.subscribe`, `monitor.read`; contract extension `x-filesquid-action`) and is wrapped in the same guard, so no handler runs before the caller is authenticated and the action authorised. The 404 and 405 fallbacks answer only an authenticated caller. Host-served routes (`GET /api/v1/events`, `/metrics`) use the same guard, which also covers the methods they do not accept. A host that installed no authoriser refuses every call. Full health, the contract and the event channel are not public. The server's static UI is public, because it is a client-rendered build with no private content ([ADR 031](./031-vanilla-typescript-ui-and-white-label-theming.md)).
- **One public route (owner decision).** `GET /api/v1/health/live` is public on purpose, for process supervisors and load balancers. Its route-table entry carries the action `public` and the contract gives it `security: []`, so it reads as a decision, not a gap. The exception cannot spread: building the router fails if any other route declares `public`, and the guard that hosts use for their own routes never bypasses authentication, whatever its action. It answers only `{"status":"up"}`: no version, component detail or journal. Full health (`GET /api/v1/health`) stays behind the credential.
- **Credentials.** `Authorization: Bearer <token>` on every request, WebSocket upgrades included. A present `Authorization` header that is not a usable `Bearer` credential is refused as `invalid_credentials` and never falls back to the subprotocol. A browser cannot set headers on a WebSocket, so an upgrade may instead offer the subprotocols `filesquid.events.v1` and `filesquid.bearer.<token>`; the token entry counts only when `filesquid.events.v1` is offered too, and the server selects `filesquid.events.v1`, never the token entry. Tokens are 256 random bits as 64 hex characters, compared as SHA-256 digests in constant time, so timing reveals neither content nor length.
- **Desktop.** The host generates a new token at every launch, keeps it in memory, installs it as the only credential, and gives it to its own pages through a webview initialization script that defines `window.__FILESQUID_LAUNCH_TOKEN__` only when the page origin is one of the app's origins: its own scheme origins in every build, plus the Vite dev-server origins in debug builds only. The scheme handler answers the CORS preflight of app origins, which a cross-origin request with `Authorization` needs. Event delivery to the app's webviews is recorded under Decision 4 (Task DE-F1.1).
- **Server, until accounts exist.** The administrator token (`FILESQUID_ADMIN_TOKEN`, or, on Unix, one generated into `$FILESQUID_DATA_DIR/admin-token` with owner-only permissions) authorises every guarded call. A configured or stored token must have the generated format, 64 hexadecimal characters (256 bits); otherwise the server refuses to start, naming the variable or file and the format but never the value. The token file is host I/O and lives in `filesquid-server`. The token file exists only on Unix; on other platforms the server never reads or writes it and refuses to start until `FILESQUID_ADMIN_TOKEN` is set (recorded 2026-10-18 after three review rounds of file-handling edge cases, to keep the file handling small). On Unix it fails closed: the file is opened once with `O_NOFOLLOW | O_NONBLOCK`, and the opened handle must be a regular file owned by the server user with no group or other permission bits; otherwise the server refuses to start and names the remedy for that case: delete `$FILESQUID_DATA_DIR/admin-token` when it is a symbolic link or not a regular file, `chown` it when another user owns it, or `chmod 600 "$FILESQUID_DATA_DIR/admin-token"` when others can read it. A first start creates the file atomically, so two servers starting together on one data directory agree on one token, and removes a partly written file if the write fails. A blank owner-only file left by a crashed first start is replaced atomically (a temporary file with a random name, then rename) after waiting at most 50 x 20 ms for a concurrent writer. Startup never deletes temporary files, because one may belong to a concurrent server's recovery; thanks to the random names, an orphan left by a crash never blocks a later recovery.
- **Seams for accounts.** An `Authenticator` turns a token into a `Principal` (today `Owner` or `Administrator`), and a `Policy` decides whether a principal may perform an action on a `Resource` (today `Host`). Accounts, sessions, groups and collection-level permissions (API-F1.9) add principals, resources, an authenticator and a policy; the guard does not change.
- **Denials.** An `ApiError` with `reason`: `missing_credentials` (401 `unauthorized`), `invalid_credentials` or `not_permitted` (403 `forbidden`). None is retryable and none repeats the credential. The journal records refusals plus credential issue (owner decision): every refusal as `api.auth.denied` (actor, reason as error code, and as target the action, or `no_route` for a 404 or 405 fallback), and `api.auth.token_issued` for the desktop's per-launch token at launch and for the server's administrator credential at every start, after the monitor starts. Successful calls are not journaled one by one; what they change is journaled as the operations they cause. A refusal before the monitor starts has no journal yet, so its entry is printed to stdout as JSON regardless of `RUST_LOG`, in addition to the INFO line the default filter shows; stdout is not a durable record.

Recorded 2026-10-18T06:09:21Z (owner decision): **Content handles for media elements.** `<img>`, `<video>`, `<audio>` and `<source>` fetch their `src` without author headers, so they cannot send `Authorization`, and [UI-S-014](../../apps/filesquid/ui/resources/srs.md) keeps tokens out of URLs. A media element therefore loads file bytes through a content handle: an opaque, read-only capability for exactly one file version, minted by an authenticated client. A content handle is not a token: it is never accepted where a token is, and a token is never accepted where a handle is. The requirement is [API-S-018](../../apps/filesquid/crates/api/resources/srs.md); [API-F1.3](../../apps/filesquid/crates/api/resources/plan.md) builds it.

- **Minting.** A client with a Bearer credential calls `POST /api/v1/content-handles` for one file object, one OCFL version and one logical path. The call is authorised exactly like the ranged content read of that file version (same action, same resource, deny-by-default); a refusal is the same refusal that read would get. A content handle cannot mint another handle. The answer carries the handle, its relative URL `/api/v1/content/<handle>` and its absolute expiry (RFC 3339 UTC); the client prefixes the host's API base (`filesquid://localhost` or `http://filesquid.localhost` on the desktop, the page's own origin on `filesquid-server`).
- **The handle.** 256 random bits from the operating system's CSPRNG (at least 128 bits are required), written as 43 base64url characters without padding. It is unguessable and is not derived from the token, a key or the file. `filesquid-api` keeps only its SHA-256 digest, in memory only; handles are never persisted.
- **The content route.** `GET` and `HEAD /api/v1/content/<handle>` in the `filesquid-api` router, so the desktop scheme and `filesquid-server` serve it unchanged. The handle in the path is the route's only credential; an `Authorization` header is neither required nor a substitute. It serves the bytes of the one file version the handle names, with the same `Range` handling and caps as the ranged content read (a satisfiable range answers `206` with `Content-Range`, an unsatisfiable one `416` with `Content-Range: bytes */<length>`, and each answer through the desktop scheme stays within its 16 MiB buffer cap). It grants nothing else: no other file, version, route or method.
- **Expiry.** An idle timeout of 300 seconds (5 minutes), restarted at mint and at the start of each accepted request, and an absolute lifetime of 3,600 seconds (60 minutes) from mint, whichever comes first. Expiry is checked only when a request starts: a response that has started is never cut off. Why these values: a fixed 5-minute lifetime would break any video that plays longer than 5 minutes, because a media element keeps issuing new `Range` requests as it plays and seeks (and through the desktop scheme each answer holds at most 16 MiB, so a 100 MB file takes at least 7 requests spread over the playback). The sliding idle window keeps playback and seeking working while keeping an unused or leaked handle short-lived, and the absolute lifetime bounds how long any one handle can be kept alive. A video that is paused for more than 5 minutes, or plays for more than 60, gets a refused request; the UI then mints a new handle and resumes at the same position ([UI-S-014](../../apps/filesquid/ui/resources/srs.md)).
- **Invalidation.** A handle ends with the credential that minted it: on the desktop at relaunch (the store is in memory and the per-launch token changes); on `filesquid-server` when the token rotates, at logout or session end, and at restart. On `filesquid-server` the policy is evaluated again at the start of every request, so a permission withdrawn after minting takes effect at once.
- **Bound.** At most 1,024 live handles per issuing credential. Minting another evicts that credential's least recently used handle; expired handles are removed when minting. A playing video stays recently used, so it is not evicted by thumbnails minted after it.
- **Denial.** An unknown, malformed, expired, evicted or revoked handle, or one whose policy check now fails, gets one identical answer: `403 forbidden`, `reason` `invalid_credentials`, not retryable, never `401` or `404`, with the same status, headers and `ApiError` fields; a `GET` carries the same body, and a `HEAD` the same status and headers with an empty body. No file is read before the handle is accepted, so the answer says nothing about whether the file exists.
- **Redaction.** A handle is treated like a token: it is never logged, journaled, echoed in an error, used as a metric label or rendered. A host that records request paths records the template `/api/v1/content/{handle}`. Minting is a credential issue and is journaled as `api.content_handle.issued` (actor, opaque file ID, version, absolute expiry; never the handle); a refused handle is journaled as `api.auth.denied` like any refusal.
- **Response headers.** Every content route answer, denials included, carries `Referrer-Policy: no-referrer` (so a document loaded from the handle URL never sends that URL onward), `Cache-Control: private, no-store` (private bytes never land in a webview, browser or proxy disk cache; caching would gain little because every mint makes a new URL, and media elements keep their in-memory buffer, so seeking within buffered data is unaffected), `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox` (an uploaded HTML or SVG file opened through its handle URL cannot run script or load anything on the API origin). A success also carries `Accept-Ranges: bytes` and the file's stored media type.
- **Not in scope here.** Whether `<img>` and `<video>` play through the desktop scheme on WebKitGTK, WKWebView and WebView2 stays S1 item (a), measured under API-F1.3 with content handles. `read()` with `fetch` and `Authorization` remains the way to read bytes everywhere else (downloads, hashing, workers).

**6. Errors.** Every route returns typed errors defined in the contract. A failed request MUST NOT crash a host ([U-26](../product-vision.md#one-api-hosts-and-distributions)).

Recorded 2026-10-17 (owner decision, Task API-F1.1):

- **Error body.** Every 4xx and 5xx response produced by the `filesquid-api` router carries the `ApiError` schema: `code` (an `ErrorCode`), `message` (for people; never paths, SQL or internal error text) and `retryable`. This includes the router's own fallbacks under `/api/v1/`: an unknown path answers `not_found` and a known path called with the wrong method answers `method_not_allowed`. Each code has one HTTP status: `invalid_request` 400, `unauthorized` 401, `forbidden` 403, `not_found` 404, `method_not_allowed` 405, `conflict` 409, `internal` 500, `unavailable` 503. Only `unavailable` is retryable. An internal failure is logged to stdout; the activity journal receives a redacted record (operation and error code only). Failures that happen in a host before or around the router are outside this guarantee and belong to the host binding tasks: on the desktop, a custom-scheme request the handler cannot convert or a response it cannot build ([DE-F1.1](../../apps/filesquid/crates/desktop/resources/plan.md)); on the server, transport and proxy failures and paths outside `/api/v1/`, such as the static UI ([SV-F1.1](../../apps/filesquid/crates/server/resources/plan.md)). Recorded 2026-10-18 (Task DE-F1.1): the desktop scheme handler answers its own failures with the same `ApiError` body, a request address it cannot route as `invalid_request` (journaled as `desktop.scheme.request`) and a response it cannot buffer as `internal` (journaled as `desktop.scheme.response`), both with operation and error code only.
- **Host routes.** A path that a host serves instead of the `filesquid-api` router, today only the event channel `GET /api/v1/events`, carries the OpenAPI extension `x-filesquid-host-route: true`. The drift test exempts exactly these paths from the router comparison.

## Rationale

One router means one implementation of every feature and one place to test it. A `tower::Service` is the common interface Axum already uses, so the server host is a thin mount and the desktop host is a thin adapter.

HTTP resources keep the browser's native handling of previews, `Range` requests, caching and uploads, which matter for collection-scale performance. A WebSocket-only API would rebuild all of that by hand, could not run on the desktop without a port, and could not be intercepted by a Service Worker. One event channel adds push where HTTP is weak. Hiding the transport in `FileSquidClient` keeps the choice reversible after S1.

The custom URI scheme keeps ADR 002's privacy property (no listener another local process could reach) while letting the desktop UI use the same HTTP API as the server UI.

Content handles (Decision 5, 2026-10-18) keep native media elements, with their `Range` reads and seeking, on the same HTTP API without putting a token in a URL. A handle is minted only by a caller that could already read the file, names one file version and expires on its own, so a handle that leaks through a URL exposes one file for at most 60 minutes, and beyond 5 minutes only while it keeps being used, not the library for the session.

## Assumptions

Verified at writing (2026-10-15):

- Tauri 2 provides `Builder::register_uri_scheme_protocol` and `Builder::register_asynchronous_uri_scheme_protocol`. Pages see `<scheme>://localhost/<path>` on macOS, iOS and Linux and `http://<scheme>.localhost/<path>` by default on Windows and Android, with an `https` option ([tauri 2.12.4 `Builder` docs](https://docs.rs/tauri/latest/tauri/struct.Builder.html)). The workspace currently pins `tauri` 2.11.5; the method is confirmed against the 2.12.4 docs, and the pinned version MUST be checked when the desktop handler is written.
- `tauri::ipc::Channel` is "an IPC channel, used to stream values from Rust to the frontend" ([docs.rs](https://docs.rs/tauri/latest/tauri/ipc/struct.Channel.html)). Tauri documents channels as fast and ordered, and events as not designed for low latency or high throughput ([Calling the frontend from Rust](https://v2.tauri.app/develop/calling-frontend/)).
- Axum WebSocket support is behind the crate feature `ws` (axum 0.8.9, [axum::extract::ws](https://docs.rs/axum/latest/axum/extract/ws/index.html)). The workspace uses axum 0.8 and tower 0.5.
- The WebSocket opening handshake creates its request with service-workers mode "none", so a Service Worker never sees it ([WHATWG WebSockets, opening handshake](https://websockets.spec.whatwg.org/#websocket-opening-handshake)).
- `EventSource` builds an ordinary fetch request without setting service-workers mode to "none" ([WHATWG HTML, server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)). Whether a Service Worker can usefully answer a long-lived event stream in every target browser is **not verified**; S1 item (d) measures it.

Not yet verified:

- Webview playback of `<video>` with `Range` requests answered by a custom scheme handler on WebKitGTK, WKWebView and WebView2. S1 item (a) measures it, through content handles (Decision 5), including that each webview honours `Cache-Control: no-store` without breaking seeking.

Assumed for content handles (Decision 5, 2026-10-18): media elements fetch their `src` without author request headers, so they cannot send `Authorization` ([WHATWG HTML, media element resource fetch](https://html.spec.whatwg.org/multipage/media.html#concept-media-load-resource)); browsers and webviews honour `Referrer-Policy` and `Content-Security-Policy` response headers on documents loaded from the handle URL.
- The OpenAPI generator crate and TypeScript generator. Candidates seen at writing were `utoipa` (crates.io 6.0.0) and `openapi-typescript` (npm 7.13.0). Verified again on 2026-10-17 (`cargo search utoipa`: 6.0.0; `npm info openapi-typescript`: latest 7.13.0). The owner decided (2026-10-17) to adopt `openapi-typescript` for the TypeScript types and no Rust generator; see Decision 2.

## Alternatives Considered

- **Tauri IPC commands per feature (previous ADR 002 model):** A second API surface beside HTTP for the server, and no native `<img src>` or `Range` reads. Rejected.
- **Per-engine view APIs and client adapters (ADR 028 Decisions 2 and 4):** Three contracts and three adapters per host. Rejected in favour of one API.
- **WebSocket only:** Loses previews, `Range`, caching and Service Worker interception, and needs a loopback port on the desktop. Rejected unless S1 shows otherwise.
- **Loopback HTTP server on the desktop with a per-launch token:** Same transport everywhere, but opens a port and breaks ADR 002. Kept as the S1 comparison, not adopted.
- **Generating the contract from Rust (`utoipa`):** Would derive OpenAPI from annotated handlers and types. Rejected by the owner (2026-10-17): the hand-written contract stays the reviewed source of truth, adds no Rust dependency, and drift tests already tie it to the Rust routes and types.
- **GraphQL or gRPC-web:** Adds a second schema system and a runtime the browser does not need for file bytes. Rejected.
- **Media authentication: token in the query string** (`?token=`): puts the session credential in URLs, history and logs, where it unlocks the whole library. Rejected by UI-S-014 and the owner (2026-10-18).
- **Media authentication: cookies:** cookies on a custom scheme behave differently on each webview, the desktop page origin differs from the scheme origin, and a cookie sent automatically needs CSRF protection the Bearer design avoids. Rejected (2026-10-18).
- **Media authentication: `fetch` into a `blob:` URL:** works with `Authorization`, but the whole file must be read into memory before playback and the element loses `Range` reads and seeking. Kept for small files read through `read()`, rejected for previews (2026-10-18).
- **Media authentication: stateless signed URLs (HMAC of file, version and expiry):** cannot be revoked when the issuing credential ends without keeping state anyway, and ties URL safety to a server key. Rejected in favour of random handles held in memory (2026-10-18).
- **Media authentication: loopback port for media only:** breaks ADR 002 and T-049 and still needs a credential. Kept only as the fallback named in S1 (a) if a webview cannot play through the scheme.

## Consequences / Implications

Easier: every UI and every host share one contract; adding a host means writing an adapter, not routes; the desktop and server UIs run the same code.

Harder: `filesquid-api` needs contract drift tests and the TypeScript generator in the local pre-commit hook; the desktop custom-scheme handler buffers each response body, so file-content endpoints MUST answer bounded, capped `Range` requests (S1 results); the event channel has two implementations (WebSocket and Tauri channel) behind one client interface; `filesquid-server` needs accounts, groups and collection permissions before multi-user release. The Origin differs per platform for custom schemes, so CORS and Content Security Policy settings MUST be tested on each OS.

Content handles (Decision 5, 2026-10-18): easier, native `<img>` and `<video>` previews are expected to work with `Range` reads on both hosts with no token in a URL, to be confirmed on each desktop webview by S1 item (a) under API-F1.3. Harder: `filesquid-api` keeps a bounded in-memory handle store tied to credentials; a second credential carrier must be tested for redaction and for identical denials; the UI must re-mint and resume when a paused or long video's handle expires; `no-store` means a preview that is shown again is fetched again.
