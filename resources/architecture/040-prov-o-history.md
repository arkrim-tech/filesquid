# Architecture Decision Record - FileSquid

040-prov-o-history.md

## Title

PROV-O history of every OCFL version, independent of C2PA, from a stand-alone `filesquid-prov` module

## Status

Accepted

Accepted: 2026-10-19. Owner decision of 2026-10-19 (option B): full W3C PROV-O history is part of the FileSquid MVP (phases F0 to F3, gate Task FS-3.9), built from OCFL versions and linked to the activity journal, and does not depend on the `c2pa` module. Owner decisions on the record contents (2026-10-19, items A to K) are written into Decisions 1 to 9: one activity per committed operation and OCFL version (A); the covered changes and the exclusions of caches, previews and no-op saves (B); failed and refused attempts in the journal only (C); entities and relations (D); agents (E); names inside the owner's library (F); operation, journal and object-version links (G); same-commit storage (H); a one-time reconstruction from inventories (I); API, the PROV-O tab of the file panel and JSON-LD export (J); and a stand-alone `filesquid-prov` crate (K). The finer points of placement, storage path and prerequisites are this record's recommendations, accepted when the owner merges it. Amends [ADR 015](./015-prov-o-jsonld-and-c2pa-sdk.md) (PROV-O history is no longer produced by, or coupled to, the C2PA engine), [ADR 026](./026-filesquid-provenance-engine.md) (the C2PA engine keeps only an optional projection of C2PA actions into the PROV-O profile), Decision 6 of [ADR 037](./037-c2pa-in-release-2.md) (the `filesquid-core` PROV-O types are no longer C2PA leftovers: they are extended for the MVP) and the journal entry shape of [ADR 033](./033-activity-journal-and-live-health-monitoring.md) (Decision 6 below). Owner answers to this record's open questions (2026-10-19), written into Decisions 1, 4 and 5 and the Consequences: a single-file download is journaled only and creates no PROV-O record; server accounts are their own agents acting on behalf of the installation (planned, finalised in Task FS-3.10); the `prov` module's optional `ocfl` feature is an allowed optional cross-module dependency.

## Context / Requirement Reference

- Requirements: [PRD F-067](../prd.md#f-067-prov-o-history-of-every-version-and-change) (new), [PRD F-042](../prd.md#f-042-ocfl-preservation-and-portable-recovery), [PRD F-061](../prd.md#f-061-activity-journal-and-live-health-monitoring), [PRD F-065](../prd.md#f-065-file-version-history-and-retention), [PRD F-046](../prd.md#f-046-media-metadata-inspection-correction-and-privacy-exports), [PRD F-043](../prd.md#f-043-c2pa-records-and-action-disclosure), vision [U-78](../product-vision.md#c2pa-module), [U-89](../product-vision.md#prov-module), [FE-082](../product-vision.md#prov-o-history), [T-037](../product-vision.md#canonical-ocfl-state-and-evidence), [T-058](../product-vision.md#canonical-ocfl-state-and-evidence), [C-056](../product-vision.md#release-sequence), [T-052](../product-vision.md#api-and-hosts).
- Until now the only PROV-O requirement was one criterion inside F-043 (C2PA records). [ADR 015](./015-prov-o-jsonld-and-c2pa-sdk.md) and [ADR 026](./026-filesquid-provenance-engine.md) placed the PROV-O projection in the `filesquid-c2pa` engine, and [ADR 037](./037-c2pa-in-release-2.md) moved that engine to release 2. The MVP therefore had no component that writes PROV-O at all.
- What exists today (inventory of `main` and the open pull requests, 2026-10-19): the `filesquid-core` types of CO-0.8 (`ProvOSidecar {time, context, profile_version, activity, ephemeral, retained}`, with no entity, agent, used or generated, and nothing persists it; its `PROV_O_CONTEXT` constant is `https://www.w3.org/ns/prov#`, which is not the PROV namespace IRI `http://www.w3.org/ns/prov#` declared by the [PROV-O ontology](https://www.w3.org/ns/prov-o)); OCFL inventories with `created`, `message`, `user` and `state` per version, where `VersionMeta::with_user` exists but no caller sets `user`; the in-memory `CommitReceipt {object_id, version, created, inventory_digest, written, took_over}`; the activity journal `JournalEntry {id, time, host, process_id, actor, operation, outcome, level, target_ids, duration_ms, error_code}` in `<data dir>/filesquid.sqlite`; catalog receipts and pending intents keyed by operation ID (DE-0.2), and DE-0.3 writing `filesquid.operation.v1 {operation_id, revision, ...}` into the version message of the library snapshot object.
- Gaps that make a version-to-journal history impossible today: (1) no `ocfl.commit` journal entry exists, and the engine's "published version" event is stdout only; (2) `JournalEntry` has no operation ID and no object and version, so journal rows join receipts and OCFL versions only by timestamp; (3) no commit sets the OCFL version `user`, and metadata edits (MD-0.2) commit the constant message `Edit metadata.md` with no operation ID; (4) metadata writes produce no journal entry and the `fsquid` CLI journals nothing; (5) repair consent and repair outcomes share no run ID, and lease takeovers reach the journal without object and version; (6) the per-library catalog outbox bypasses the journal writer, so its entries raise no `journal.entry` event and no metric; (7) browser console warnings never reach the journal.
- Owner rule (2026-10-19, [logging-enforce.md](../../.agents/rules/logging-enforce.md) section 2): no event class may be exempted from the journal for volume reasons, and OCFL versioning is part of "logging": every single thing that happens ends up in a record.
- FileSquid's modularity principle: module crates build, test and publish on their own and MUST NOT take a default dependency on another module; the `metadata` module's optional `ocfl` store is the precedent for an optional one ([ADR 027](./027-filesquid-metadata-pluggable-stores.md), [ADR 029](./029-filesquid-unified-product-and-distributions.md)).

## Decision

1. **PROV-O history is independent of C2PA; what it covers.** The unit is one `prov:Activity` per committed OCFL version, for library snapshots, files, metadata edits and repairs alike (owner decision A: one activity per committed operation, which is one OCFL version). When one operation commits more than one object (an import commits the file object and the library snapshot), each object version gets its own activity, and the activities share the operation ID; there is never an activity without its version or a version without its activity. Every committed change produces one: import (and upload and copy), rename, move, hide, unhide, delete, restore, purge (permanent delete), metadata edit (including version labels), export, scrub, revert (and reinstate), repair, and catalog organisation (collections, virtual collections and their memberships) (B). It is written in FileSquid's versioned JSON-LD profile, in every build, whether or not the `c2pa` module is linked. Excluded: caches and previews (T-037), and no-op saves: a command that changes nothing commits no version and produces no record at all (B). Failed and refused attempts stay in the activity journal only; PROV-O describes what happened to files (C). A single-file download creates no PROV-O record: it is recorded in the activity journal only (owner decision, 2026-10-19). An export, a scrubbed export, a ZIP download and a share or publication output produce new output, so each remains a PROV-O activity, recorded in the library's history object (Decision 5). When the `c2pa` module is enabled (release 2), C2PA actions link to the PROV-O activity of the same operation by its operation ID; the C2PA engine's optional projection (C2PA-S-011) targets this same profile. Ephemeral caches (thumbnails, decoded frames, transient computations) produce no record unless their output is retained or disclosed ([T-037](../product-vision.md#canonical-ocfl-state-and-evidence)).

2. **Engine placement: a new stand-alone module crate, `filesquid-prov`, plus application meaning in `filesquid-api`.**
   - `filesquid-prov` (`apps/filesquid/crates/prov`, module plan prefix `PV`, SRS prefix `PROV-S`) owns the generic PROV-O model and profile: `prov:Entity`, `prov:Activity`, `prov:Agent` (with `prov:SoftwareAgent`; the owner is a plain `prov:Agent`, never a `prov:Person`, per Decision 4), the relations `prov:used`, `prov:wasGeneratedBy`, `prov:wasDerivedFrom`, `prov:wasInvalidatedBy`, `prov:wasAssociatedWith`, `prov:wasAttributedTo` and `prov:actedOnBehalfOf`, `prov:startedAtTime` and `prov:endedAtTime` as RFC 3339 UTC; JSON-LD serialization with an embedded context; bounded parsing and validation of records against the profile; a builder that turns caller-supplied version facts (object ID, version, created, user, message, logical-state diff with digests) into a record; and an in-memory history index (by entity, activity, agent, operation and time). Its default build depends on no other FileSquid crate (not even `filesquid-core`), never depends on `filesquid-native` or `filesquid-c2pa` with any feature (owner decision K), links no Axum, Tauri, SQLite, libvips or FFmpeg, does no filesystem or network I/O and builds for `wasm32-unknown-unknown`.
   - An optional `ocfl` Cargo feature, off by default, adds `filesquid-ocfl`: it reads and writes records as logical files in an OCFL object through the engine's change model, and derives backfill records from OCFL inventories (Decision 7). This is the second optional cross-module dependency after the `metadata` module's `ocfl` store, under the same rule: never a default dependency.
   - `filesquid-api` keeps the FileSquid meaning: which operation is which activity kind, which agents took part, the link to journal entries, redaction for exports and shares, the backfill job, and the query routes. It links `filesquid-prov` with the `ocfl` feature.
   - Later (release 1) `filesquid-prov` is published like the `ocfl` and `metadata` crates, and its stand-alone commands (`fsquid prov show`, `log`, `validate`, `export`) join the one `fsquid` CLI ([ADR 036](./036-single-fsquid-cli.md)).

3. **Same-commit storage, no extra version.** The PROV-O record of a version is written in the same OCFL commit as the change it describes, so a normal change creates exactly one version, as before. A record is at most 1 MiB (the parsing bound of PROV-S-004); an operation whose entities do not fit, such as a large batch import or snapshot, writes further parts `provenance/<version>-2.jsonld`, `-3` and so on in the same commit, each at most 1 MiB and each repeating the activity node, and Task FS-3.4 measures record sizes on the Large fixture. The record is the logical file `provenance/<version>.jsonld` of the same object, where `<version>` is the OCFL version name exactly as the inventory spells it (for example `provenance/v3.jsonld`); media type `application/ld+json`, UTF-8. Because the version name and the inventory `created` time are fixed only when the engine reserves `vN` (and change again when a commit is rebased onto a moved head, OCFL-S-016), the record is produced by a caller-supplied function that the change model calls after the reservation and before the inventory is written, with the reserved version name and `created` time (prerequisite IO-1.5). The record's activity end time equals the inventory `created` time. The logical-path prefix `provenance/` is reserved in FileSquid's OCFL application profile; the drive browser hides it as it hides each file's metadata record `<file-uuid>.metadata.md` (which, since the owner decision of 2026-10-19, also holds the import facts that [ADR 038](./038-import-file-record.md) first put in `file-record.md`). [T-046](../product-vision.md#canonical-ocfl-state-and-evidence) allows JSON in an OCFL object when a named requirement requires the format; F-067 is that requirement.

4. **Profile `filesquid-prov/1`.** A record is one JSON-LD document using the W3C PROV-O vocabulary. W3C publishes PROV-O as an OWL ontology (`https://www.w3.org/ns/prov-o`, namespace `http://www.w3.org/ns/prov#`) but no JSON-LD context document (`https://www.w3.org/ns/prov.jsonld` answered 300 Multiple Choices, not a context, when checked on 2026-10-19), so the profile embeds its context: it maps `prov:` to `http://www.w3.org/ns/prov#`, `xsd:` to `http://www.w3.org/2001/XMLSchema#` and `fsq:` to the FileSquid profile vocabulary `https://filesquid.tech/ns/prov/v1#`; readers never fetch a context over the network. It carries `fsq:profile: "filesquid-prov/1"` and a `@graph` with:
   - exactly one `prov:Activity` per committed version, identified `urn:filesquid:activity:<operation-id>:<object-id>:<version>`, with `fsq:operation` (the operation ID; shared by every object version one operation commits), `fsq:kind` (the operation kind), `prov:startedAtTime`, `prov:endedAtTime`, and `fsq:journalEntry` (the opaque IDs of the journal entries of this commit, Decision 6);
   - a `prov:Entity` per file and metadata state the version used, generated or invalidated (owner decision D), identified `urn:filesquid:entity:<object-id>:<version>:<percent-encoded logical path>` and carrying the OCFL object ID, version, logical path and SHA-256 digest; a generated state `prov:wasGeneratedBy` the activity and `prov:wasDerivedFrom` the state it replaces (a move derives the new logical path from the old one with the same digest; a rename, which changes only the display name, and a metadata edit derive the new `<file-uuid>.metadata.md` from the previous one; the stored original `<file-uuid>.<ext>` never changes its name); a deleted or purged state `prov:wasInvalidatedBy` the activity; inputs are `prov:used`; the activity names the OCFL object and version it committed (`fsq:objectVersion`) (G);
   - the `prov:Agent`s (owner decision E as corrected on 2026-10-19): for the owner, the **installation agent**, a plain `prov:Agent` identified `urn:uuid:<installation-uuid>`, with no `prov:Person`, person identity, account or display name; the FileSquid host as a `prov:SoftwareAgent` with product, distribution and version (no host name) acting on the installation's behalf (`prov:actedOnBehalfOf`); and a tool or model `prov:SoftwareAgent` reserved for later AI actions. The installation UUID is a UUID v4 ([ADR 021](./021-uuid-v4-identifiers.md)) that the host generates once, on the first start that finds none, from a cryptographic random source; it is stored in `<data dir>/installation.json` (owner-only) and in the host's operational store, read at every start so it is the same value across restarts and updates, restored from whichever copy survives, and restored with a backup of the data directory. When both copies are lost the host generates a new one and journals `host.installation.created`; earlier records keep the value they name, and it is never derived from hardware, account or host names. `prov:wasAssociatedWith` links the activity to each agent that took part, and generated entities are `prov:wasAttributedTo` the installation agent. Desktop records name only these agents. **Server accounts (planned approach, owner decision 2026-10-19, finalised in Task FS-3.10):** on `filesquid-server` each account gets a UUID v4 when it is created and is its own `prov:Agent`, identified `urn:uuid:<account-uuid>`, with no user name, e-mail address or display name; it `prov:actedOnBehalfOf` the server's installation agent, and an activity a signed-in user caused is `prov:wasAssociatedWith` that account agent as well as the host's software agent.
   The profile is versioned: a change that removes or retypes a field is `filesquid-prov/2`, and readers MUST read every earlier profile. FileSquid's `filesquid-core` constant `PROV_O_PROFILE_VERSION = 1` names this profile, and its `PROV_O_CONTEXT` is corrected to the namespace IRI `http://www.w3.org/ns/prov#` (nothing persists the old value).

5. **Where each record lives.** A record describing an object's version lives in that object, so an object copied alone still explains its own history. Activities that change no library object but produce new output (an export, a scrubbed export, a ZIP download, or a share or publication output) are recorded in a per-library **history object**: one OCFL object per library whose versions each add one `provenance/<version>.jsonld` record (and its journal entries) and nothing else. A single-file download adds no version there; it is journaled only (Decision 1). A version-inventory repair (OCFL-S-020) adds no version and may not change logical state, so its activity (with its repair run ID) is committed as a provenance-only version of the repaired object right after the repair, under a new reservation; if that commit fails, the journal still holds the repair entries and the provenance commit stays a pending intent that is retried, never dropped. These provenance-only versions are the only versions that exist for the record alone.

6. **Prerequisites (journal and commit linkage).** Before records can link to the journal, FileSquid closes inventory gaps 1 to 6:
   - `JournalEntry` gains `operation_id` (optional) and `object_ref` (optional, `urn:uuid:<object-id>@vN`), stored as columns in the SQLite journal (`filesquid-native`) and later in the PostgreSQL journal of `filesquid-server` (SV-F1.2); both are opaque and pass the existing redaction rules.
   - Every commit, by every writer (the API's change-model path, the metadata store, the desktop OCFL coordinator), emits an `ocfl.commit` journal entry with the operation ID, object and version, the takeover flag of the receipt and the outcome; a lease takeover entry names the object and version.
   - Every commit sets the OCFL version `user` (name `FileSquid installation`, address `urn:uuid:<installation-uuid>`) and the structured message `filesquid.operation.v1 {"operation_id", "kind", "revision"?, "label"?}`, including metadata edits (MD-0.2's constant message is replaced). A version label set at commit time ([F-065](../prd.md#f-065-file-version-history-and-retention)) is the message's `label` member, and the API shows it as the label.
   - Every metadata write is journaled (`metadata.edit`), and repair consent, repair outcome and the provenance commit share one repair run ID.
   - Catalog outbox entries go through the journal writer, so they raise `journal.entry` events and count in the metrics like every other entry.
   - Journal entry IDs of a commit are assigned before the commit, so the record can name them; the entries themselves are written in the catalog transaction that stores the receipt. When a crash leaves a published version without its journal entries, reconciliation at open (the library reconcile of DE-0.3; DE-S-011) writes them from the version's PROV-O record with the same IDs, so a link never dangles.
   Gap 7 (browser console warnings) is a journal gap of its own; it does not block PROV-O history and is closed by the client-events route of [ADR 033](./033-activity-journal-and-live-health-monitoring.md) Decision 7 (Task API-F2.10).

7. **Backfill for objects committed before the feature.** A bounded, resumable job (registered in the process registry, checkpointed per object, capped per run, cancellable) finds every version without a record and derives one from the inventory: `created` as the activity end time, `user` as the agent when present (otherwise the agent is stated as unrecorded, never guessed), the operation ID and kind from a `filesquid.operation.v1` message when present (otherwise kind `unknown`, no `fsq:operation`, and the activity identified `urn:filesquid:activity:reconstructed:<object-id>:<version>`), and used, generated, derived and invalidated entities from the logical-state diff with the previous version. It joins journal entries by object and version where they exist and states their absence otherwise. This is a one-time, resumable reconstruction (owner decision I), re-run only when objects without records are found, for example after restoring an old copy. Each derived record says `fsq:derivation: "reconstructed"` and carries its own `fsq:recordedAt` time; it never claims to have been written at the original commit. All missing records of one object are committed in one provenance-only version of that object (their file names name the versions they describe), whose own record describes the backfill run. The job is idempotent: a version that has a record is skipped.

8. **Redaction and disclosure.** The journal keeps only opaque IDs (operation, object, version, journal and run IDs): no logical paths, names, titles or contents, as [ADR 033](./033-activity-journal-and-live-health-monitoring.md) requires. The PROV-O record is complete for the owner's own library: logical paths, digests, agents, and names and descriptive content such as the original file name and titles MAY appear in it (owner decision F); it adds nothing the object's inventory and metadata record do not already hold, and it stays in the owner's library, its copies and its recovery. On export and share the [F-046](../prd.md#f-046-media-metadata-inspection-correction-and-privacy-exports) outgoing policy applies: an owner archival export carries the records unchanged; a share or publication output excludes them by default or, when the owner selects them, carries them redacted per the F-046 policy (agent identities, names, titles and identity-bearing logical paths removed), and the preview says so. Links from records to journal entries carry opaque IDs only (F).

9. **Query and display.** `filesquid-api` serves the history of a file, an object version, an operation and a time range as paged routes (`x-filesquid-action` `history.read`, the file's read permission), plus the raw JSON-LD record of a version. An operational index of the records MAY exist in the catalog and MUST be rebuildable from the OCFL records. The default UI's file panel has four tabs with one look and behaviour (File facts, Descriptive, PROV-O, Audit log; owner decision 2026-10-19). The **PROV-O** tab lists a file's activities, entities and agents as property/value rows newest first, with a link to their journal entries for the owner or an administrator, and lets the owner export the history as JSON-LD; the **Audit log** tab lists the file's journal entries, links each entry of a committed operation to its PROV-O activity and labels failed and refused attempts as journal-only (they have no activity) (owner decision J).

10. **CO-0.8 extension.** `filesquid-core` gains the FileSquid-facing contract: `OperationKind`, the `filesquid.operation.v1` message type with format and parse, `VersionRef {object_id, version}`, `JournalLink {operation_id, journal_entry_ids}` and `HistoryEntry` (the API and UI summary of one activity); `ProvOSidecar` keeps the T-037 retained/ephemeral gate and gains the version reference, operation and journal link; the PROV namespace constant is corrected. The full PROV-O graph stays in `filesquid-prov`; `filesquid-api` maps one onto the other.

## Rationale

- **Independent of C2PA:** the MVP's promise is durable, recoverable, versioned file management. A history of what happened to each file is part of that promise and of the owner's "everything ends up in a record" rule; C2PA is a signing and disclosure standard for media that arrives in release 2. Coupling the two left the MVP with no history writer at all.
- **A module crate:** a PROV-O history of OCFL versions is useful to preservation programmes that never run FileSquid, exactly like the `ocfl` and `metadata` engines; the modularity principle asks for it to be a stand-alone crate. A crate also gives the C2PA engine's optional projection one profile to target, and keeps PROV-O vocabulary out of `filesquid-api`, which stays application meaning. The optional `ocfl` feature follows the ADR 027 precedent and keeps the default build free of other modules.
- **Same commit:** writing the record in the commit it describes keeps history and content atomic (no version without its record, no record for a version that was never published), costs no extra versions, and lets an ordinary copy of the storage root carry the full history. A rebase recomputes the record because the version name changes.
- **Pre-assigned journal IDs:** the record must name journal entries that are written after the OCFL publication (the catalog transaction stores the receipt after the version exists); pre-assigning the IDs and repairing missing entries at reconcile closes that ordering gap without a second write path.
- **Installation agent:** inventories and records are read by ordinary tools after copying; person names, accounts and host names would leak identity into every copy, and the desktop has no account. An installation UUID says which FileSquid installation acted, stays stable across restarts and reveals nothing else.

## Assumptions

- The OCFL change model can call a caller-supplied function after reserving `vN` and before writing the inventory without weakening the write order of OCFL-S-018 (IO-1.5 tests this).
- Record size is small next to content for ordinary operations (a few kilobytes per version); batch operations split into 1 MiB parts (Decision 3). One extra logical file per version does not change the MVP performance budgets; Task FS-3.4 measures it.
- `https://filesquid.tech/ns/prov/v1#` can serve a human-readable vocabulary page later; records do not depend on it because the context is embedded.
- A desktop MVP has one owner, so the agent set on desktop is the installation, the desktop host and, later, tools; on `filesquid-server` each account is its own agent acting on behalf of the installation (Decision 4), which Task FS-3.10 finalises with the account store.

## Alternatives Considered

- **C2PA-only PROV-O (the ADR 015 and ADR 026 coupling):** PROV-O only as a projection of C2PA actions inside `filesquid-c2pa`. Rejected: no history until release 2, none for files and actions C2PA does not cover (folders, library snapshots, metadata-only edits, repairs), and the owner's history would depend on a signing engine.
- **Projection computed on demand, without storing:** derive PROV-O from OCFL inventories and the journal whenever it is asked for. Rejected: the journal is operational data that is not inside the OCFL root, so a copied or recovered library would lose agents, operation kinds and journal links; inventory facts alone cannot say who acted, which tool ran or which operation a version belonged to. It is kept only as the backfill method for versions committed before this decision.
- **PROV-O engine inside `filesquid-api`:** fewer crates and no new module plan. Rejected: the history engine would not be usable without the FileSquid API, contrary to the modularity principle, and PROV-O vocabulary would spread into the application layer.
- **Extend `filesquid-core` with the full PROV-O model:** rejected: `filesquid-core` is FileSquid's shared vocabulary, which stand-alone users of a module should not need; it keeps only the FileSquid-facing summary contract (Decision 10).
- **One append-only history file per object (rewritten each version):** rejected: it changes an existing logical file in every version (more bytes, harder rebase) and loses the one-to-one mapping between a version and its record.
- **A provenance-only version after every change:** rejected: it doubles the versions of every object and leaves a window where a version exists without its history.

## Consequences / Implications

- Easier: every MVP library carries a portable, standards-based history of every version and change, readable with a JSON parser after copying the storage root; journal rows and OCFL versions join by operation ID and object version instead of by timestamp; the release-2 C2PA engine links to an existing history instead of starting one.
- Harder: every writer (API change-model path, metadata store, desktop coordinator) must produce a record in the same commit; the change model gains a version-bound file hook; journal schema migrations add two columns; provenance-only versions exist for exports, repairs and backfill; the backfill job must be honest about missing agents and journal links.
- The MVP grows by global Task FS-2.8 (76 hours; the file panel tabs and the Journal tab that show the history are in Task FS-2.9) and release 1 by the crate's publication and CLI commands (PV-F3.1, 6 hours); Task FS-3.9 depends on Task FS-2.8.
- [AGENTS.md](../../AGENTS.md) section 15 and [src-isolation.md](../../.agents/rules/src-isolation.md) list the `prov` module's optional `ocfl` feature next to the metadata module's optional `ocfl` store as the two allowed optional cross-module dependencies, under the same rule: never a default dependency, and no dependency on `filesquid-native` or `filesquid-c2pa` (owner decision, 2026-10-19).
- The journal's two new fields are part of the entry shape of ADR 033 Decision 2 ("Content").
